# Продажи → Смены

Раздел финансовых итогов Quick Resto: `/sales/shifts`. Это финансовые рабочие дни, отдельные от смен сотрудников в графике работы. Зарплата, ФОТ, питание, премии, посещаемость, отправки в Adesk и Telegram пока остаются в существующих процессах.

## Данные и расчёты

- Рабочий день CHILLING: 09:00–09:00, Europe/Moscow. Дата строки — дата начала дня.
- Оборот: действующие гостевые чеки, без Staff, чаевых, депозитных позиций, парковки и сервисного сбора; скидки учитываются в строках чека.
- Staff определяется по клиенту `payer.id` и группе 8 из отчёта гостей. Колонка содержит сумму чеков, не количество. Всего чеков — все действующие чеки, включая Staff.
- Чаевые и пополнения депозитов: подписанные количества специальных позиций из кассовых отчётов. Остатки и расходование депозитных счетов не участвуют. Сервис — надбавка действующих чеков, включая Staff.
- Кальяны: существующий отчёт 216. Бар: оборот минус кальяны. Итоги округляются до целых рублей.
- Такси: `front.encashment`, `typeTransaction=cashOut`, назначение содержит «такси». Сохранено окно старого процесса 09:00–06:00 и формат его запроса.
- Пустое значение означает отсутствие данных. Ноль означает известный нулевой результат. Если источника для показателя нет, сумма не подменяется нулём.

Публичное чтение `/platform/online/api` остаётся на Basic Auth. Бэк-офис `/platform/data` использует существующую сессию Keycloak. Для CHILLING адрес бэк-офиса — `https://chilling.quickresto.ru`, публичного API — `nx815`. На живой проверке одинаковые чеки у `nx815` в бэк-офисе не содержали `payer`, а у `chilling` содержали. Поэтому адрес бэк-офиса берётся из настройки подключения, с проверкой HTTPS и домена Quick Resto. Учётные данные не передаются в браузер.

Пока поддерживается одно заведение на подключение. Автообновление второго заведения этого аккаунта блокируется. При нескольких внешних заведениях нужен отдельный этап проверки привязки касс, чеков и кальянного отчёта; неподтверждённые фильтры не используются.

## Хранение и обновление

`sales_days` хранит отдельно расчёт, ручные исправления и архив первоначальных значений. Эффективные значения применяют исправления поверх расчёта. Производные бар и чаевые со сбором пересчитываются, кроме полей с собственным исправлением. Исправление требует причину и ожидаемую версию строки; отмена исправления возвращает расчёт. Журнал содержит автора, причину, значения до/после и изменения производных сумм.

История пересчитывается напрямую из Quick Resto по текущим правилам. Первоначальный архив сохранён только в базе для аудита, не участвует в расчётах и не имеет активного подключения или интерфейса импорта. Пересчёт не затрагивает ручные исправления.

Независимый обработчик обновляет текущий день раз в 15 минут. После 09:45 проверяет завершённые дни последних семи дней, по текущим правилам. Закрытый день нельзя опубликовать без закрытых кассовых отчётов.

Очередь хранит страницы чеков, детали, шаги отчётов и курсоры в базе. Страница и её курсор фиксируются атомарно. Каждый запуск имеет блокировку и токен владения; устаревший обработчик не может сохранить срез или итог. Чеки, группы клиентов и локальные строки загружаются страницами, без обрезания на 150/1000. Дата каждого чека проверяется. Для текущего дня верхняя граница чеков фиксируется моментом создания запуска, чтобы новые чеки не сдвигали страницы.

После загрузки всех источников итог публикуется атомарно. Ошибка сохраняет последнюю успешную сумму и исправления. Ответ 429 сохраняет курсор и включает общую паузу подключения, включая другие обработчики. Остальные ошибки после трёх попыток останавливают запуск; автоматический новый запуск имеет задержку 15 минут. Нормализованные исходные чеки сохранены для аудита в закрытой таблице, недоступной ролям браузера. Они содержат только поля расчёта, без имён и контактов.

Владельцу доступны все пять прав `sales.*_shifts`. Управляющему (`custom_manager`) по умолчанию доступны просмотр, исправления и экспорт. Остальным ролям права выдаются явно. RLS ограничивает данные текущим аккаунтом и заведением; пользовательские роли не могут писать в таблицы напрямую или запускать служебные функции очереди.

## Запуск

1. Применить миграции `supabase/migrations/242_sales_shifts.sql` и `supabase/migrations/243_sales_sync_rate_limit.sql` к нужной базе. Production требует отдельного согласования.
2. В существующей интеграции Quick Resto настроить публичный доступ и бэк-офис. В карточке заведения, вкладка «Продажи», проверить правила и включить обновление. Здесь же запускается пересчёт периода до 366 дней.
3. Настроить `CRON_SECRET` на сервере. Секрет нельзя помещать в `NEXT_PUBLIC_*`, файлы репозитория, URL или журнал.
4. Запустить `npm run sales:worker` (Node >=20.12). Для локальной проверки адрес по умолчанию `http://localhost:3400`; другой задаётся `SALES_WORKER_ORIGIN`. Обработчик читает `.env.local` и вызывает защищённый POST `/api/cron/sales-shifts` с заголовком `X-Cron-Secret`.
5. В production вместо отдельного процесса допустим n8n Schedule Trigger раз в минуту → HTTP POST на этот маршрут с тем же заголовком. Вычисления, очередь, исправления и аудит остаются в Sheerly. Запуск старых процессов зарплаты и Adesk не меняется.

Текущий день имеет приоритет над архивным пересчётом. Обработчик не зависит от открытого браузера. Страница только отслеживает состояние очереди. Экспорт использует текущие фильтры и сортировку, все строки периода и только видимые колонки; права проверяются сервером. Настройки колонок и размера страницы сохраняются по заведению через общие компоненты лаборатории `/dev/table-lab`.
