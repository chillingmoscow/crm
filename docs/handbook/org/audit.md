# Журнал событий

## Что это

Раздел **Организация → Журнал** (`/org/audit`) — общая лента всех
заметных действий в аккаунте: кто, когда и над каким объектом
что-то поменял. Покрывает все основные блоки приложения:

- сотрудники (приём, увольнение, восстановление, перевод, обновление
  контактов и HR-данных);
- приглашения (отправка, отмена, принятие);
- должности и их права;
- транзакции, счета, статьи доходов/расходов, контрагенты;
- заведения, юрлица, настройки аккаунта;
- база знаний (создание, переименование, перемещение, удаление,
  блокировка от редактирования, отметка «обязательно к прочтению»).

## Для кого / когда использовать

Доступно владельцу, администратору и бухгалтеру — у них есть
permission **«Видеть журнал аудита»** (`org.view_audit`). Управляющий,
хостес, официант — не видят раздел в меню.

Полезно когда:

- Идёт внутренний разбор: кто и когда что поменял.
- Сотрудника устраивают повторно — хочется вспомнить причину прошлого
  ухода (она сохраняется в журнале, даже если в карточке стёрта).
- Кто-то задаёт «куда делась эта страница» / «почему у транзакции
  поменялась сумма» / «кто заархивировал юрлицо».
- Проверка соответствия (compliance) — что админ менял в реквизитах.

## Как пользоваться

1. В боковом меню в группе **Организация** открыть **Журнал**.
2. События отсортированы от новых к старым и **сгруппированы по дням**
   («Сегодня», «Вчера», «5 мая» — текущий год без года, прошлые годы
   с годом).
3. У каждой записи:
   - иконка действия (плюс / карандаш / архив / корзина / щит и т.д.);
   - имя автора действия (актор);
   - человекочитаемая фраза с именем затронутой сущности
     (`«Иван Иванов»` для сотрудников, `«Касса №1»` для счетов, и т.д.);
   - время («5 мин назад» / «вчера» / дата);
   - ссылка на саму сущность (если ещё существует и доступна).
4. Для событий типа «обновил данные» под фразой показывается
   список изменений в формате **«поле: было → стало»** (например,
   `телефон: +79991234567 → +79998765432`).
5. Внизу — кнопка **«Загрузить ещё»**. Подгружает следующую страницу
   без полной перезагрузки, скролл сохраняется. На один клик добавляется
   50 событий.

## Фильтры

В шапке справа от заголовка — иконка-воронка с бейджем количества
активных фильтров. По клику открывает / прячет панель фильтров.

| Фильтр | Что делает |
|---|---|
| **Период** | Выбор диапазона дат + пресеты («Сегодня», «Вчера», «Текущая неделя», «Прошлый месяц» и т.д.). Календарь по-русски, выбранный диапазон подсвечен голубым. |
| **Раздел** | Multi-select из 11 разделов: Сотрудники / Приглашения / Должности / Транзакции / Счета / Статьи / Контрагенты / Заведения / Юрлица / Аккаунт / База знаний. |
| **Сотрудники** | Multi-select по списку сотрудников аккаунта (включая уволенных). Показывает события, где сотрудник участвовал — как объект действия ИЛИ как исполнитель. Если нужно строго одно — открой карточку сотрудника, там есть отдельные вкладки «Журнал» (объект) и «Активность» (исполнитель). |

Активные фильтры показываются цветными «пилюлями» с крестиком для
быстрого сброса. Кнопка **«Очистить все»** справа сбрасывает разом.

## Поиск

Иконка-лупа в шапке. По клику разворачивается в инпут на 280 px.
Поиск **глобальный** — ищет совпадения сразу по всем сущностям:

- сотрудники по имени и фамилии;
- KB-страницы по заголовку;
- должности по названию;
- приглашения по email;
- транзакции по описанию (и по номеру `#42`, если ввели число);
- счета, статьи, контрагенты — по названию;
- контрагенты дополнительно по ИНН;
- заведения по названию;
- юрлица по названию, короткому названию и ИНН.

Поиск работает И как «сотрудник = объект действия», И как «сотрудник
= исполнитель действия». Например, поиск «Анна» найдёт и то, что
делали с Анной, и то, что Анна делала с другими.

Если одновременно активен фильтр «Сотрудники» и текстовый поиск —
они работают как независимые AND-условия. Сначала ограничиваемся
выбранными сотрудниками, потом среди их событий ищем по подстроке.

URL-параметры (можно делиться ссылкой на отфильтрованную ленту):

```
/org/audit?q=Иван&types=staff,transaction&staff=<uuid>&from=2026-05-01&to=2026-05-13
```

## Журнал на карточке объекта

У большинства объектов в системе есть встроенная вкладка «Журнал»
прямо на странице — это узкий срез общего журнала, отфильтрованный по
этому объекту:

- **Сотрудник** (`/people/staff/[id]`) — две вкладки: «Журнал» (про
  него) и «Активность» (его действия). См.
  [people/staff-journal.md](../people/staff-journal.md).
- **Должность** (`/people/roles/[id]`) — вкладка «Журнал» после
  «Оплата труда».
- **Заведение** (`/org/venues/[id]`) — вкладка «Журнал» после «Карта
  залов».
- **Юрлицо** (`/org/legal-entities/[id]`) — вкладка «Журнал» рядом с
  «Основное».
- **Счёт** (`/finance/accounts/[id]`) — вкладка «Журнал» рядом с
  «Основное».

Преимущество встроенной вкладки — не нужно переходить в общий журнал
и крутить фильтры. Например, на странице юрлица сразу видно историю
изменений реквизитов.

## Журнал базы знаний

Отдельная страница **/knowledge/audit** показывает только KB-события
(создание, переименование, перемещение, удаление, восстановление,
блокировка/разблокировка от редактирования, «обязательно к прочтению»).
Полезна, когда работаешь в KB и не хочешь видеть финансовый/кадровый
шум.

Общий `/org/audit` тоже содержит эти события (раздел «База знаний» в
фильтре) — выбирай удобный.

## Что НЕ попадает в журнал

Намеренно не пишем (чтобы не зашумлять):

- Импорт транзакций из QuickResto / bank_sync / других интеграций
  (`source != 'manual'`).
- Авто-пересчёт баланса счетов после изменения транзакций.
- Изменения служебных полей: `created_at` / `updated_at` /
  `updated_by`, sort-order при drag-n-drop, jsonb с часами работы
  заведения, dadata-синхронизация юрлица.
- Системные категории и должности (`is_system = true`) — они
  засеяны миграциями, не действие пользователя.
- Имя / фамилия / гендер / аватар / адрес сотрудника (только HR-важные
  контакты — телефон, телеграм, ДР).
- KB save-edit'ы (история контента уже есть во вкладке «История версий»
  на самой странице).

## Что происходит при удалении аккаунта

При полном удалении аккаунта Postgres каскадно сносит все дочерние
сущности (заведения, юрлица, транзакции и т.д.) и их audit-записи.
Журнал самоликвидируется вместе с аккаунтом — нет «зависших» записей
от удалённых аккаунтов.

## Известные ограничения

- Журнал ведётся с момента выкатки соответствующей миграции для
  каждого блока. События до этой даты в журнал не попадают.
- Фильтр «Сотрудники» работает только для тех, у кого был хотя бы
  один UVR-ряд в любом venue текущего аккаунта (включая уволенных).
  Внешние/анонимные акторы туда не попадут.
- Поиск ограничен 200 совпадениями на тип. Если по запросу нашлось
  больше — лучше уточнить запрос или применить дополнительные фильтры.

## Где в коде

Полная картина (на случай если разработчик будет это читать):

- `supabase/migrations/035_audit_logs.sql` — таблица `audit_logs`,
  helper `log_audit()`, RLS на `org.view_audit`.
- Триггеры:
  - `074_kb_audit_triggers.sql` + `081_kb_audit_thread_events.sql` —
    база знаний.
  - `153_staff_audit_triggers.sql` — сотрудники.
  - `154_invitations_roles_audit_triggers.sql` + cascade-fix в
    `157_audit_cascade_guard_for_154.sql` — приглашения / должности.
  - `155_finance_audit_triggers.sql` — финансы.
  - `156_org_audit_triggers.sql` — venues / legal_entities / accounts.
- UI:
  - `src/app/(dashboard)/org/audit/page.tsx`
  - `src/app/(dashboard)/org/audit/_components/audit-page-client.tsx`
  - `src/components/audit/audit-event-row.tsx`
- Helpers:
  - `src/lib/audit/feed.ts` — общий resolver URL-params → запрос.
  - `src/lib/audit/list.ts` — `listAuditEvents` + entity snapshots.
  - `src/lib/audit/format.tsx` — registry action_code → фраза + иконка.
  - `src/lib/audit/search-staff.ts` — глобальный поиск + список
    сотрудников для фильтра.
  - `src/lib/audit/group-by-date.ts` — группировка по дням.
