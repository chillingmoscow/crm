# Выпуск раздела Кандидаты на self hosted Supabase

Обновление общих списков людей и «Обзора»: после резервной копии применить `20261031144659_people_overviews.sql`, затем `20261031153759_recruiting_overview_funnel.sql`. Миграции добавляют только функции чтения. Разбор дат журнала совместим с PostgreSQL 15; `pg_input_is_valid` не требуется. Проверить под действующим пользователем RPC `staff_people_overview` и `candidate_people_overview`: стаж относится к активному заведению, воронка к аккаунту и месяцу поступления. Перед выпуском приложения проверить эти же запросы на рабочей версии PostgreSQL в транзакции с откатом. Настройки интеграций и данные сотрудников/кандидатов миграции не меняют.

Обновление структуры интеграций: перед выпуском применить `supabase/migrations/20261031002045_integrations_recruiting_settings.sql`. Миграция переносит отдельный чат анкет в настройки Telegram организации и не меняет токены, ключ webhook, резерв кодов и настройки найма. Сначала миграция, затем приложение: обработчик уведомлений читает новый столбец `candidate_chat_id`. Для проверки миграции с откатом: `supabase/tests/integrations_recruiting_settings.sql`; маршрутизация чатов проверяется в `src/lib/integrations/telegram-destination.test.mts`.

Обновление группового удаления: перед выпуском интерфейса с выделением строк применить `supabase/migrations/20261030231538_candidate_bulk_delete.sql`. Группа удаляется целиком либо полностью сохраняется при ошибке; права владельца, ограничения найма, очистка файлов и журнал берутся из существующей команды удаления анкеты.

Результат выпуска: Тильда передаёт анкеты непосредственно серверу Sheerly, кандидаты хранятся на уровне аккаунта; найм выполняет шаги Quick Resto и выдаёт данные офисного замка. Этот runbook не означает, что выпуск уже выполнен.

1. Сделать резервную копию self-hosted PostgreSQL. Применить последовательно `supabase/migrations/261_people_candidates.sql`, `supabase/migrations/268_candidate_recruiting_workflow.sql`, `supabase/migrations/269_candidate_appointment_forms.sql`, `supabase/migrations/270_candidate_comments_and_meeting_actions.sql`, `supabase/migrations/271_candidate_single_interview.sql`, `supabase/migrations/272_candidate_interview_ratings.sql`, `supabase/migrations/273_candidate_hiring_parity.sql`, `supabase/migrations/274_organization_telegram.sql`, `supabase/migrations/275_candidate_hire_audit.sql` и `supabase/migrations/276_staff_termination.sql` в одной транзакции с `psql -v ON_ERROR_STOP=1 --single-transaction` от владельца закрытой схемы (в текущем self-hosted окружении — `supabase_admin`). Приложение использует существующий self-hosted Supabase, новый облачный проект не требуется. Миграции приложения не применяются через push автоматически.
2. Выпустить приложение. Проверить `NEXT_PUBLIC_SITE_URL` (публичный HTTPS адрес Sheerly), `INTEGRATIONS_ENCRYPTION_KEY` (действующий ключ существующих интеграций) и `CRON_SECRET`. Не заменять ключ шифрования: им зашифровано подключение Quick Resto.
3. Запустить отдельный процесс `pnpm candidates:worker` с `CANDIDATES_WORKER_ORIGIN`, указывающим на внутренний адрес приложения, либо вызывать защищённый `POST /api/cron/candidates` каждые 15–60 секунд с заголовком `x-cron-secret`. Обработка не зависит от открытого браузера. Существующие payroll/sales worker продолжают работать отдельно.
4. Проверить права управляющего. Новые права выдаются владельцу и стандартным ролям управляющего/администратора. Для нестандартных должностей выдать необходимые права явно. Настройку интеграций и перенос кодов выполняет владелец.
5. До переключения обновить экспорт октябрьских анкет и обсуждений Notion. Сухой запуск: `node scripts/import-candidates-notion.mjs --file /private/path/export.json --account ACCOUNT_UUID`. После проверки — тот же запуск с `--apply --allow-remote`. Экспорт содержит персональные данные; хранить вне Git с правами 600. Повторный запуск дополняет комментарии/файлы, но сохраняет уже внесённые в CRM изменения анкеты. Записи со статусом «Принят на работу» требуют отдельного сопоставления и автоматически не создают сотрудников.
6. Сверить число анкет, статусы, авторов и даты сообщений. Проверить перенос фото: недоступные исходные файлы помечаются отдельно. Старые URL Uploadcare не являются постоянным хранилищем CRM.
7. Перед первым новым наймом получить актуальный пул занятых номеров/кодов замка после завершения созданий сотрудников из Glide и перенести его в настройки найма. Зарезервировать также номера без парного кода. Проверить сопоставление должностей с Quick Resto, группы гостей, бонусного счёта и складов. Настройки «склад 1 всем / склад 16 мастерам / Staff 8 / тип счёта 1» взяты из прежнего сценария CHILLING и должны быть проверены для конкретного подключения. Старый сценарий создаёт данные замка, но не программирует физический замок.
8. Подключить прямой webhook в Тильде с отдельным секретом в `x-tilda-key`. Проверочный `test=test` отвечает 200 и не создаёт кандидата. Для анкеты отключить старую отправку в n8n, опубликовать страницу, сверить хвост заявок между экспортом и переключением. Общий сценарий n8n не отключать: он принимает и другие формы.
9. Провести согласованную реальную заявку и реальный найм. Проверить нового сотрудника/PIN/склады, гостя и его группу, бонусный счёт, данные замка, зарплатную карточку и источник смен. В локальных автоматических проверках реальные записи Quick Resto не создаются.

Ошибки доставки и подтверждения отправки Telegram остаются в журнале заданий. При неподтверждённой отправке сначала проверить чат: Telegram не предоставляет ключ идемпотентности, поэтому слепой повтор исключён. При сбое найма продолжать существующую операцию; не удалять журнал и не создавать вторую анкету. Персональные данные и ключи не помещать в логи и описание PR.

Собеседование требует даты и времени, итог «Пройдено» — комментария. После заполнения результата можно назначить стажировку с выбором заведения. Она отображается в графике отдельной записью кандидата, не создаёт смену сотрудника или зарплатную карточку. Найм и связь с существующим сотрудником разрешены только на этапе «Стажировка»; ручная смена любого этапа сохранена.

При обновлении уже установленного раздела перед миграцией 271 проверьте, что у одного кандидата нет нескольких записей `candidate_appointments` с `kind=interview` (GROUP BY account_id, candidate_id HAVING count(*)>1). Индекс не удаляет и не объединяет историю: при повторах миграция остановится, данные нужно разобрать до выпуска. Для локальной базы эта проверка выполнена, повторов нет.

Telegram организации настраивается в «Настройки → Интеграции → Telegram». Токен вводит владелец; приложение проверяет бота и доступ к чату, хранит токен только зашифрованным. Новые анкеты и сообщения о найме используют этого бота; отдельный чат кандидатов может переопределить общий чат. Старое подключение кандидатов сохраняется как совместимый резерв. Секреты не попадают в журнал настроек.

Отдельный чат анкет не меняет чат сообщений о найме: для найма используется общий чат организации. При выпуске CHILLING сохраняются прежние разные чаты старших и команды.

В настройках найма заведения укажите ссылку на чаевые из прежнего сценария. Гость Quick Resto получает телефон отдельным дочерним контактом `crm.customer.contacts` типа `phoneNumber`: вложенное поле `tokens` в создании гостя не подходит. Публичное чтение требует `Content-Type: application/json`. Создания через публичный API выполняются без сетевого повтора; при неоднозначном ответе сохраняется started и проверяется результат, повторное создание блокируется.

После найма владельцу в карточке сотрудника доступен просмотр выданных данных замка. Программирование физического замка остаётся ручным, как в прежнем n8n.

Перед переключением найма оставить только один источник новых данных замка. Старый сценарий n8n не видит выдачи из CRM: после окончательной сверки занятого пула прекратить запуск его ветки создания сотрудников и выдачи кодов. Общий приём других форм не отключать. Локальный тест не меняет действующий сценарий n8n.

Штатное увольнение (миграция 276) сохраняет профиль и историю, выключает членство/зарплатную карточку/квалификацию графика и создаёт задание удаления внешнего доступа. Обработчик `/api/cron/candidates` продолжает незавершённые увольнения; состояние и повтор доступны в карточке сотрудника. При другом активном заведении аккаунта общий QR и замок сохраняются. Сначала удаляется QR-сотрудник, затем проверяются склады, нулевые бонусные счета закрываются и удаляются, после них удаляется гость. Каждый шаг подтверждается чтением, ненулевой остаток/холд останавливает удаление гостя без списания денег. Чужие или расходящиеся внешние связи блокируют команду. После удаления внешнего доступа простое восстановление членства запрещено: требуется новое оформление.

Код замка отзывается в CRM, зашифрованное значение удаляется, резерв номера/хеша сохраняется. Если код устанавливался в физический замок, управляющий должен удалить его вручную: интеграции управления физическим замком нет. Это явно указано в карточке. Права `people.edit_staff` проверяются в выбранном заведении; самоувольнение и увольнение владельца запрещены. Служебные задания закрыты RLS и недоступны клиенту напрямую.
