# Дизайн: горячие клавиши для действий со страницей в Базе знаний

Дата: 2026-05-19

## Контекст

В прошлой итерации добавлен экран-справка «Горячие клавиши»
(`src/components/shared/hotkeys-dialog.tsx`, реестр `src/lib/hotkeys.ts`,
открытие по `Shift + ?` и кнопкой в меню профиля). Глобально работают
`Cmd/Ctrl+K` (поиск по KB из любого раздела) и `Cmd/Ctrl+B` (сайдбар).

Внутри Базы знаний у открытой страницы есть полноценное меню действий
(`kb-page-menu.tsx`, монтируется в `knowledge/[slug]/page.tsx:310` —
т.е. только когда страница открыта), но **ни одно из этих действий не
имеет хоткея**. Пользователь, который весь день работает в KB, вынужден
тянуться в ⋯-меню для частых операций (заблокировать перед расшариванием,
добавить в избранное, дублировать как шаблон, посмотреть историю).

Цель: повесить хоткеи на набор частых действий со страницей KB, показать
их в существующей справке, не дублируя тонкую логику этих действий.

## Объём (согласовано с пользователем)

Набор для ежедневного использования — 5 действий:

| Действие | Клавиши | Условие | Почему не другая буква |
|---|---|---|---|
| Заблокировать / разблокировать страницу | `Mod+Shift+L` | `canLock` | — |
| В избранное / из избранного | `Mod+Shift+F` | — | — |
| Дублировать страницу | `Mod+Shift+D` | `canDuplicate` | — |
| Создать новую (корневую) страницу | `Mod+Shift+P` | `canCreate` | `Cmd+Shift+N` = инкогнито браузера, не перехватывается |
| История версий | `Mod+Shift+H` | `canViewVersionHistory` | `Cmd+Shift+V` = вставка без формата, конфликт с редактором |

`Mod` = ⌘ на macOS, Ctrl на остальных (как уже сделано в hotkeys-dialog).
Если соответствующего права/возможности нет — команда выполняет no-op с
тостом «Недостаточно прав» (то же поведение, что уже у пунктов меню;
переиспользуется их guard, ничего нового не пишем).

`Mod+Shift`-комбинации не порождают текст, поэтому гард «фокус в
input/textarea/contenteditable» **не нужен** — достаточно
`preventDefault()`. (В отличие от `Shift + ?`, где гард обязателен.)

Известный мелкий конфликт: `Cmd+Shift+H` в Safari — «Домой».
`preventDefault()` для этой комбинации в Safari срабатывает, действие
браузера подавляется. Зафиксировано осознанно.

## Архитектура

### Принцип

Не дублировать orchestration действий. Например, `onToggleLock` в
`kb-page-menu.tsx` перед глобальным lock'ом **флашит pending-save**
(связано с миграцией `086_kb_save_page_strict_lock.sql`); favorite/lock
ведут optimistic-стейт через `kb-page-state-overrides-store`. Хоткей
обязан вызывать **те же** обработчики, а не свою копию логики.

Поэтому — командная шина (одобренный подход A): KB-level keydown-листенер
переводит сочетание в команду, а компоненты, которые уже владеют
состоянием и обработчиками, её исполняют. Это повторяет принятый в
кодовой базе паттерн (`CustomEvent("hotkeys:open")` в sidebar/hotkeys-dialog,
`window`-keydown в `kb-collection-block.tsx`).

### Юниты

**1. `src/lib/kb-hotkeys.ts` — чистый матчер (без побочных эффектов)**

```ts
export type KbCommand =
  | "toggle-lock" | "toggle-favorite" | "duplicate"
  | "create-page" | "version-history";

// Возвращает команду или null. Никакого DOM/preventDefault внутри.
export function matchKbHotkey(e: {
  key: string; shiftKey: boolean; metaKey: boolean; ctrlKey: boolean;
}): KbCommand | null;
```

Что делает: чистое отображение «поля события → команда». Зависимостей нет.
Тестируется изолированно.

**2. `src/lib/kb-hotkeys.test.mts` — node:test**

Таблица: каждое сочетание → ожидаемая команда; негативные кейсы (без
Shift → null; только Mod → null; чужая буква → null; и meta, и ctrl
варианты дают команду на разных платформах).

**3. `KbHotkeyListener` — клиентский компонент-листенер**

- Монтируется один раз в `knowledge/layout.tsx` (KB-scope: на индексе/
  корзине/аудите страницы нет, команды просто никто не исполнит — но
  листенер дешёвый и stateless).
- `window` `keydown` → `matchKbHotkey` → при не-null:
  `e.preventDefault()` + `window.dispatchEvent(new CustomEvent("kb:command", { detail: { command } }))`.
- Никакого состояния. Что делает: превращает клавиатуру в события
  команд. Зависит только от матчера.

**4. Подписчики команд (исполнители) — переиспользуют существующие
обработчики**

- `kb-page-menu.tsx` — добавить `useEffect`, слушающий `"kb:command"`.
  На `toggle-lock` → существующий `onToggleLock()` (с его flush-before-
  lock и canLock-guard); `toggle-favorite` → `onToggleFavorite()`;
  `duplicate` → существующий duplicate-handler; `version-history` →
  `setVersionsOpen(true)` (если `canViewVersionHistory`). Компонент уже
  знает `pageId`, права и состояние открытой страницы — ничего не
  прокидываем дополнительно.
- `kb-tree-nav.tsx` — подписка на `create-page` → существующий
  `onCreateRoot()` (тот же, что у кнопки «+ Новая страница»; serverside
  всё равно проверяет `kb.create_pages`).

Граница: листенер ничего не знает про права и состояние; исполнители
ничего не знают про клавиши. Связь — одно событие `kb:command` с
дискриминированным `command`.

### Поток данных

```
keydown ─▶ KbHotkeyListener ─ matchKbHotkey ─▶ CustomEvent("kb:command")
            (preventDefault)                         │
                                  ┌──────────────────┴───────────────┐
                          kb-page-menu                          kb-tree-nav
                   (lock/favorite/duplicate/                  (create-page →
                    version-history → существующие             onCreateRoot)
                    handler'ы)
```

### Обработка ошибок / краевые случаи

- Нет прав: исполнитель — no-op + тост (уже реализовано в обработчиках
  меню; не дублируем).
- Несколько `kb-page-menu` в дереве не монтируются одновременно (меню
  принадлежит одной открытой странице) → одна команда = одно исполнение.
  Если в будущем появится несколько — добавить guard «исполняет только
  активная страница» (вне текущего объёма, отметить в плане).
- Команда пришла, но нужного исполнителя нет в DOM (например, `create-page`
  на странице без дерева на мобиле) → событие игнорируется, ничего не
  падает.
- `Esc`/закрытие диалога истории версий — штатно через существующий
  компонент.

## Тест-план

1. `node --test --experimental-strip-types src/lib/kb-hotkeys.test.mts` —
   зелёный.
2. `pnpm exec tsc --noEmit` + `pnpm lint` — зелёные.
3. Dev-сервер, открыть страницу KB:
   - `Mod+Shift+L` → страница блокируется/разблокируется (тумблер в меню
     отражает то же состояние); при отсутствии `canLock` — тост.
   - `Mod+Shift+F` → toggle избранного (звезда в меню синхронна).
   - `Mod+Shift+D` → создаётся дубликат, переход на него.
   - `Mod+Shift+P` → создаётся новая корневая страница (как кнопка «+»).
   - `Mod+Shift+H` → открывается диалог истории версий; `Esc` закрывает.
4. На `/knowledge` (индекс, без открытой страницы) сочетания page-уровня
   не делают ничего деструктивного.
5. Сочетания работают, когда курсор в редакторе (не блокируются гардом)
   и не ломают ввод текста.
6. Справка (`Shift + ?`) показывает новые строки; на Win/Linux — `Ctrl`.

## Вне объёма (YAGNI)

- Переназначаемые пользователем хоткеи.
- Хоткеи на экспорт / удаление / шаблон / обязательное чтение (не входят
  в «ежедневный» набор; высокий риск случайного деструктива для delete).
- Создание именно дочерней страницы текущей (берём корневую — совпадает
  с видимой кнопкой «+», наименее неожиданно).
