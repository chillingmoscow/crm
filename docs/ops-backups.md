# Бэкапы продовой базы

## Зачем это здесь

До 30 августа 2026 у продовой базы crm **не было бэкапов вообще**. Единственный
артефакт — ручной дамп от 26 февраля, снятый перед миграцией.

На той же машине при этом лежала ночная задача `woord-backup.sh` от соседнего
проекта. Она ходила в контейнер `supabase-db-q24gc87hd6op291zogvgf5yr`, который
к тому времени был удалён, и падала **116 ночей подряд**. Сам скрипт вёл себя
правильно: `set -e`, честный ненулевой код возврата. Не сработало другое — cron
писал вывод в файл и никого не оповещал, поэтому четыре месяца никто ничего не
замечал. Последний валидный дамп в хранилище — от 5 мая, и он от чужого проекта.

Отсюда устройство того, что описано ниже: бэкап без оповещения о сбое и без
проверки восстановлением — это не бэкап, а надежда.

## Что и когда выполняется

Скрипты лежат в репозитории (`scripts/`), на сервере — копии в `/usr/local/bin/`.
Конфиг — `/root/.crm-backup-env` (режим 600), в репозиторий не попадает.

| Когда (UTC) | Что | Лог |
| --- | --- | --- |
| ежедневно 02:30 | [`prod-backup.sh`](../scripts/prod-backup.sh) — дамп, проверка, отправка в S3, чистка старых | `/var/log/crm-backup.log` |
| ежедневно 09:00 | [`prod-backup-watchdog.sh`](../scripts/prod-backup-watchdog.sh) — ругается, если бэкапа не было >48 ч | `/var/log/crm-backup.log` |
| воскресенье 03:30 | [`prod-backup-verify.sh`](../scripts/prod-backup-verify.sh) — восстановление в одноразовый контейнер и сверка | `/var/log/crm-backup-verify.log` |

Хранилище — Timeweb S3, бакет `woord-backups`, префикс `crm/`. Отдельный бакет
завести не вышло: Timeweb не даёт создавать бакеты через S3 API. Чистка каждого
скрипта строго ограничена своим префиксом, чтобы соседи не удаляли чужое.

Срок хранения — 30 дней (`BACKUP_RETENTION_DAYS`).

## Что лежит в хранилище

На каждый прогон три файла с общим именем `crm-<ISO-дата>`:

- `.dump` — `pg_dump --format=custom --compress=9` базы `postgres`. **Владельцы
  и права не вырезаны**: без `GRANT` для `anon`/`authenticated` восстановленная
  база отдаёт PostgREST «permission denied for table» ещё до RLS (грабли из
  миграции 047).
- `.roles.sql` — `pg_dumpall --roles-only`. Роли живут на уровне кластера и в
  `pg_dump` не попадают, а без них не расставить владельцев.
- `.meta` — размер, sha256 и число строк ключевых таблиц на момент снятия.
  Именно по нему еженедельная проверка доказывает, что данные восстановились, а
  не просто открылся файл.

## Оповещения

Письма уходят через уже настроенный SMTP (Yandex Postbox, отправитель
`noreply@sheerly.app`) на адрес из `BACKUP_ALERT_EMAIL`.

- **«CRM: бэкап базы НЕ СДЕЛАН»** — ночной прогон упал, в письме хвост лога.
- **«CRM: бэкапа нет N часов»** — сторож не увидел свежей отметки об успехе.
  Приходит именно тогда, когда письма об ошибке не будет: скрипт не упал, а
  вовсе не запускался.
- **«CRM: бэкап проверен восстановлением»** / **«CRM: бэкап НЕ ВОССТАНАВЛИВАЕТСЯ»**
  — итог еженедельной проверки.

Порог сторожа — `BACKUP_MAX_AGE_HOURS` (48). Учтите: значения из файла конфига
перекрывают переменные окружения, потому что файл читается через `set -a` уже
после старта скрипта.

## Как восстановить

Порядок для настоящей аварии — не тот, что в еженедельной проверке (она работает
в песочнице без суперпользователя, см. ниже).

```bash
# 1. Взять свежие файлы из хранилища
set -a; . /root/.crm-backup-env; set +a
LATEST=$(docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY \
  amazon/aws-cli:latest --endpoint-url "$AWS_ENDPOINT_URL" \
  s3api list-objects-v2 --bucket "$BACKUP_BUCKET" --prefix crm/ \
  --query "reverse(sort_by(Contents[?ends_with(Key,'.dump')],&LastModified))[0].Key" --output text)
```

```bash
# 2. Скачать дамп и роли в /root/restore
mkdir -p /root/restore && cd /root/restore
docker run --rm -e AWS_ACCESS_KEY_ID -e AWS_SECRET_ACCESS_KEY -v /root/restore:/out \
  amazon/aws-cli:latest --endpoint-url "$AWS_ENDPOINT_URL" \
  s3 cp "s3://$BACKUP_BUCKET/$LATEST" /out/crm.dump
```

```bash
# 3. Роли — первыми, иначе не расставятся владельцы
docker cp /root/restore/crm.roles.sql supabase-db-jk8o8os4wowowg088ksckcc4:/tmp/
docker exec supabase-db-jk8o8os4wowowg088ksckcc4 \
  psql -U supabase_admin -d postgres -f /tmp/crm.roles.sql
```

```bash
# 4. Сам дамп — под supabase_admin, он владелец большинства объектов
docker cp /root/restore/crm.dump supabase-db-jk8o8os4wowowg088ksckcc4:/tmp/
docker exec supabase-db-jk8o8os4wowowg088ksckcc4 \
  pg_restore -U supabase_admin -d postgres --clean --if-exists /tmp/crm.dump
```

После восстановления сверить `supabase_migrations.schema_migrations` с числом
файлов в `supabase/migrations/` — реестр пассивный, и если дамп старше
последних накатов, недостающие миграции нужно применить руками (см. memory
`self_hosted_supabase.md`).

## Что проверка НЕ проверяет

Еженедельная проверка поднимает чистый `supabase/postgres` и разворачивает дамп
в свежую базу с `--no-owner --no-privileges`. Так пришлось из-за устройства
образа: роль `postgres` там не суперпользователь, владельцы в дампе —
`supabase_admin`, а зайти под ним в одноразовый контейнер нельзя (пароль не
задан, а сменить его без суперпользователя невозможно).

Отсюда честная граница: проверка доказывает, что **данные** восстанавливаются
целиком — таблицы на месте и число строк совпадает с `.meta`. Она **не**
доказывает, что корректно раскладываются владельцы и `GRANT`. В самом дампе они
есть; проверить их можно только настоящим восстановлением в поднятый стек.

Пять ошибок `pg_restore` в отчёте — ожидаемый шум на объектах `vault`/`pgsodium`,
которыми владеет сам образ Supabase. К нашим данным они отношения не имеют.

Вторая граница: сторож живёт на той же машине и в том же cron. Умрёт машина
целиком — промолчит и он. Полностью это закрывает только внешний пинг
(healthchecks.io и подобное) — одна строка `curl` после успешного прогона.

## Проверить руками

```bash
ssh root@185.178.44.60 /usr/local/bin/prod-backup.sh
```

```bash
ssh root@185.178.44.60 /usr/local/bin/prod-backup-verify.sh
```

Проверить, что канал оповещений жив, проще всего подменив отметку об успехе:
записать в `/var/lib/crm-backup/last-success` старую дату, запустить сторожа и
вернуть значение обратно.
