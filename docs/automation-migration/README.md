## Первый кодовый этап

`src/lib/automations/payroll-rules.ts` переносит чистое принятие решений для медкнижек,
формы, задач, праздников и стажа. Он читает явный снимок данных и сохранённую версию
правил и возвращает решения/необходимые уточнения. Ни SQL-записей, ни HTTP-вызовов нет.

- Один штраф за случай просрочки, по решению владельца; не ежедневное начисление.
- Отсутствующая книжка отличается от ещё не сверенных данных. Неизвестное состояние
  прежней компенсации блокирует повторную компенсацию.
- Дата обследования и срок действия книжки раздельны; требование книжки по должности
  и сопоставление должности для подарков должны быть подтверждены.
- Подарки читают числовые суммы, точные пороги стажа и ограничения получателей.
  Целевая скидка возвращается отдельным решением: назначения скидки в QR ещё нет.
- Расписание формы получает явную дату первого удержания, не создаёт её задним числом;
  последняя часть закрывает точный остаток в копейках. Исторические части передаются
  без пересчёта. Создание первоначального расхода не входит в этот расчётный модуль.
- Неподтверждённая задача не штрафуется. Одно выполнение имеет один ключ результата:
  изменение исхода должно идти через сверку/исправление, а не создавать вторую запись.
  Если исправление уже учтённой задачи убирает финансовое последствие, модуль явно
  возвращает её на сверку; прежний штраф не пропадает из отчёта и не отменяется сам.
- Отсутствие медкнижки и стаж привязаны к устойчивому ID эпизода работы, а не к дате
  приёма. Исправление даты не создаёт новый штраф или подарок; повторный приём имеет
  другой ID. При отсутствии этого сопоставления решение остаётся на проверке.
- Идентичность события не включает версию правила. Уже сверенные ключи из старого
  учёта исключаются из новых решений и возвращаются отдельно для сравнения исхода/суммы.
  Изменение настроек или исправление даты в том же случае просрочки не даёт права
  повторить подарок или штраф.

Проверка: `node scripts/test-native-payroll-rules.mjs`. Обновление 29 октября:
модуль подключён к ежедневной очереди сравнения (см. ниже); финансовое исполнение
этой очередью и отключение n8n не включены.

## Обязательные следующие части

Первый обход экранов Glide и второй кодовый этап (месячная статистика) зафиксированы
в [карте экранов](glide-screens-2026-10-28.md). Это отдельная проверка полноты интерфейса;
она не меняет статус оставшихся автоматизаций. Уточнение владельца по двум сотрудникам
и найденные смены Notion также внесены в карту.

1. Сверить остаточный поток Fees/Transactions/Employees и текущие внешние операции.
   На каждый переносимый объект нужен устойчивый исходный ID; одного имени/суммы мало.
   Одинаковое событие в нативном расчёте и Fees не создаёт второй штраф. Финансовые
   расхождения сначала оформляются точным планом, без автоматического переигрывания.
2. Перенести состояние процессов: компенсации, покупки/части формы, задачи, подарки,
   незавершённые диалоги, очередь актов и внешние операции. Суммы/права/связи без
   подтверждённого источника оставлять на проверке.
3. Ввести журнал исполнения/outbox, ограничения по счёту и объекту, атомарный захват,
   историю попыток, подтверждение провайдера и единственный возврат исходной операции.
   Обрыв POST — неизвестный результат: сначала сверка, затем решение, не слепой retry.
4. Подключать нативные обработчики по функциональным цепочкам с тестами и сверкой.
   Доступность экрана или чистого расчётного модуля не означает переноса всей цепочки.
5. Перед передачей проверить опубликованные версии n8n повторно: сценарии продолжают
   меняться. Завершить текущие исполнения, закрыть старые входы и запретить retry старых
   финансовых записей. Только после этого включать нового владельца внешних действий.
6. Проверить реальные согласованные случаи, повторы, обрывы и отмены; убедиться, что
   старые источники больше не нужны. Выключенные служебные пробы сохранить как архив,
   не превращать их в новые рабочие задания.

В ходе этой проверки workflows n8n не выполнялись, не публиковались и не выключались;
финансовые операции и реальные бонусы не менялись. 29 октября по отдельным ответам
владельца созданы две карточки без входа, Назира уволена датой 5 октября, исправлены
её ошибочные последующие выходы. Снимок до исправления сохранён на сервере; журнал
содержит исходные значения. Новые права входа и приглашения не выдавались.

## 31 октября: контекст общего дня и обсуждения (следующий пакет, локально)

Владелец уточнил аудиторию: обсуждение общей смены и уведомления — только для
пользователей с `sales.view_shifts`. Участие сотрудника в смене само по себе права

Из свежего Fees прочитаны Shifts A:M (152 дня), Salary A:X (736 строк) и Comments.
По точному Row ID темы к двум общим сменам относятся четыре комментария. Остальные
темы Comments и пустая таблица App: Comments не объявлены перенесёнными. Имена авторов
сопоставлены по точному ID Employees; реквизиты и сканы для этого не читались.
Метки времени Comments конвертируются по метаданным исходной книги Europe/London
с проверкой неоднозначного времени DST; рабочий день продаж остаётся 09:00 Москва.

Миграция 284 хранит архив общего дня отдельно от индивидуальных сумм Salary.
Чтение, команды и аудит обсуждения ограничены активным аккаунтом/заведением/правами.
В карточке допродаж видны оборот связанной общей смены, команда своего направления,
доли допродаж и обсуждение; переход открывает исходный общий день. Архив не подменяется
текущей выручкой Sheerly. Нативный оборот учитывает сохранённые ручные исправления.
Карточка общей смены использует тот же вид команды; существующая сверка/выдача чаевых
сохранена. Месячный график мастеров дополнен суммой баллов, ранний период собственного
расчёта явно отделён от архива (с 16 октября).

Нативный комментарий создаётся по ключу повтора. Автор может редактировать свой;
удалить/восстановить может автор или пользователь с `sales.configure_shifts`.
Изменения требуют актуальной версии; дата и заведение проверяются сервером.
История сохраняет создание, автора, время и последующие действия, в общем журнале
есть русские названия и переход к обсуждению. Только новое создание уведомляет
активных пользователей с правом продаж, кроме автора. Уведомление содержит общую
дату, без текста комментария/сумм. Импорт, правка и восстановление не повторяют
рассылку. Повтор исходного импорта не дублирует записи; правка источника не оживляет
удалённый комментарий.
