# Этап 2: единый список исключений и доли подразделений

Дата: 2026-11-04. Решения владельца — из разговора 2026-11-04 (ответы на вопросы).

## Зачем

1. В правилах заведения исключения из недостачи — текстовое поле с 32 названиями из Glide. Расчёт его **не читает**. Реально работают только правила «Исключать всегда» из акта (по товару, 17 активных на проде). Из-за этого октябрь расходится с таблицей: лёд, трубочки, пергамент, группы «Имущество» (26 товаров), «Хозтовары» (50 товаров), «Доставка» и др. не исключаются.
2. Доли распределения редактируются во вкладке заведения в «группах подразделений». Группа на проде всегда = одно подразделение. Владелец хочет задавать долю в настройках подразделения.

## Цели

- Один список исключений: открыть → увидеть → удалить → добавить. Элемент списка — **группа, подгруппа или товар** Quick Resto. Это та же сущность, что создаёт кнопка «Исключать всегда» в акте.
- Список влияет на итоги актов и на удержание.
- 32 названия из Glide перенесены в список (что сопоставилось) и текстовое поле убрано.
- Доля (%) и участие в общей недостаче задаются на странице подразделения.

## Не цели

- Категории, закреплённые за подразделением (отложено владельцем).
- Исключения по заведению: правила остаются на уровне аккаунта (заведение одно; так же устроено «Исключать всегда»).
- Изменение формулы расчёта.

## Решения владельца

- **Действие исключения — все незакрытые месяцы.** Новое (или удалённое) исключение применяется ко всем актам, чей месяц не зафиксирован в зарплате, включая уже подведённые. Затронутые месяцы пересчитываются. «Зафиксирован» = у заведения есть `payroll_periods` за месяц со статусом не `draft` — тот же критерий, что у сторно удержаний (миграция 309).
- **Одна доля на подразделение**, без групп. Задаётся на странице подразделения. Во вкладке заведения — сводка «Всего N из 100%».
- **Список исключений** — в карточке заведения → «Инвентаризация», кнопкой «Исключения · N».

## Как устроено

### Данные

`inventory_result_exclusion_rules` расширяется до трёх видов цели:

- `target_kind`: `product` | `group` (подгруппа — это группа с родителем; отдельный вид не нужен).
- для `group` — `ingredient_group_id` (FK `(account_id, ingredient_group_id)` → `ingredient_groups(account_id, id)` + композитный индекс), `external_group_id`, имя на момент создания.
- check: ровно одна цель по виду; уникальность активного правила на цель.
- существующие строки → `target_kind = 'product'`.

Группа исключает все товары, у которых она в цепочке родителей (`ingredients.group_id` → `ingredient_groups.parent_group_id`…). Товар может попасть под несколько правил — для строки акта запоминаем одно (приоритет: товар, затем ближайшая группа).

### Применение

- Резолвер «правило для товара» (`actions-shared.ts`, сейчас по `ingredient_id`/`external_product_id`) дополняется проходом по группам. Он используется при построении/обновлении итогов — новые и открытые акты подхватят группы автоматически.
- **Ретроактивно**: при создании правила помечаем строки `document_items` во всех актах незафиксированных месяцев — и живые поля, и `finalized_excluded_from_totals` у подведённых. При удалении — снимаем только строки с этим `exclusion_rule_id` (уже так) и тоже в обоих полях, только в незафиксированных месяцах. Ручные решения по строке (ручное исключение / «вернуть в учёт» = `exclusion_rule_dismissed_at`) не перезаписываются. В журнал акта — событие. Затем пересчёт удержания по затронутым месяцам (через тот же механизм, что после подведения итогов; при выключенном автопересчёте — сообщение «пересчитайте месяц»).
- Акты зафиксированных месяцев не трогаем.

### Перенос 32 названий

Одноразово (миграция данных, идемпотентно): точное совпадение без учёта регистра/пробелов сначала с группой, затем с товаром (включая архивные). Неоднозначное (несколько товаров, напр. «Грейпфрут» — 2) и несопоставленное (напр. «Лёд / 28х28х28», «Пергамент», «Frigate», «Карамель Кремка / …») **не угадываем**: оставляем в `config.inventoryExclusions` и показываем в окне исключений блоком «Не найдено в Quick Resto — выберите вручную» с возможностью сопоставить или удалить. Когда список пуст, блок пропадает.

### Интерфейс исключений

Вкладка «Инвентаризация» заведения: вместо textarea — строка «Исключения · N» с кнопкой «Открыть». Окно (Sheet справа / bottom-sheet на мобиле, по `docs/mobile-web.md`):

- поиск-добавление: один комбобокс по группам и товарам, группы с путём («Расходные материалы → Хозтовары»), у группы — число товаров;
- список: тип (группа/товар), название, откуда (из акта / вручную / перенесено из Glide), кто и когда; удаление с подтверждением;
- блок несопоставленных названий (см. выше).

Права: смотреть — `inventory.view_results`, менять — `inventory.adjust_results` (как сейчас у «Исключать всегда»).

### Доли подразделений

- Формат правил не меняется: `groups[]` с одним подразделением на группу, `excludedDepartmentIds`. Расчёт не трогаем.
- Страница подразделения → «Основное»: блок «Недостача»: переключатель «Участвует в общей недостаче», доля %, «Применять с», «Основание». Сохранение = новая версия правил заведения подразделения (тот же `saveStockRules`, та же проверка версии). Не участвует → подразделение в `excludedDepartmentIds`.
- Вкладка заведения: таблица подразделений «доля / участвует», «Всего N из 100%», ссылки на страницы подразделений; редактирование долей там убрано. - Сумма долей участвующих подразделений должна быть 100% (схема правил это уже требует). Поэтому блок на странице подразделения при изменении доли показывает доли остальных подразделений заведения и даёт поправить их в том же окне; сохраняется одной версией. Без этого правка одного подразделения всегда упиралась бы в «сумма ≠ 100%». _(Решение исполнителя.)_
- Архивное подразделение из распределения выпадает при следующем сохранении; до этого блок показывает предупреждение.
