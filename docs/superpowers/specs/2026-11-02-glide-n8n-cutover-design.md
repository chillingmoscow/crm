## 1. Зачем

Сейчас учёт живёт в трёх местах одновременно: Glide (интерфейс и кнопки),
Google-таблица `Fees` (фактическая БД, 23 листа), n8n (72 сценария, исполнитель
реальных операций) и Sheerly (новые экраны и расчёты). Пока источников больше
одного, любое действие нужно дублировать, а любое расхождение приходится разбирать
руками. Цель — один рабочий контур в Sheerly.

Владелец 2 ноября: «чем быстрее переключиться, тем лучше; просто для этого нужно
полностью всё перенести, чтобы учёт и вся работа были в одной системе».

## 2. Решения владельца, зафиксированные 2 ноября

Это его слова, не мои предположения.

| Тема | Решение |
| --- | --- |
| Модель перехода | Переносим **по одному сценарию**. Перенесли → отключили соответствующий сценарий n8n. Не «большой взрыв» |
| Adesk | Работает **в параллель**. Отказ от него — отдельный следующий этап, после переноса его данных в Sheerly и проверки |
| Telegram (MTProto) | **Остаётся** и работает отдельно в дополнение к Sheerly. Складская Telegram-цепочка (списания, акты приготовления) пока не переносится |
| Будущее Telegram | В перспективе от связки откажемся: сотрудники будут заходить в Sheerly и присылать фотографии и пометки туда |
| Коэффициент 1,1 | **Отменён.** В новую систему не переносим |
| Менеджеры в недостаче | **Участвуют**, своим подразделением |
| Удержание по недостаче | **Не штраф.** Динамическое значение, отдельная строка в ведомости — «списание по недостаче» |
| Создание сотрудников | Только в Sheerly. В Glide сотрудники больше не создаются |
| Хвосты выплат | Согласованы ранее — проводить |
| Стаж | Включается 10 ноября, без тестов |
| Ведомость в ноябре | Платим **по Google-таблице**. Расчёт Sheerly должен с ней **сходиться**; расхождение — повод разобраться, а не платить по Sheerly |
| Два источника | Удержание складывается из **двух** сумм: недостача по актам инвентаризации и акты списаний, которые заводят сотрудники (разбили графин — списали). Суммируются |
| Охват недостачи | На личные списания недостача не раскладывается |
| Излишки | **Зачитываются** против недостач между актами, по суммам: −5 000 ₽ в одном акте и +2 000 ₽ в другом дают −3 000 ₽ к удержанию |
| Границы зачёта | **Внутри пула плательщиков.** Излишек кальянного склада уменьшает недостачу кальянов, но не недостачу всей команды |
| Лимит | 10 000 ₽ — **общий на заведение** за календарный месяц, но только на общий пул: инвентаризация общих складов плюс акты списаний |
| Куда лимит не идёт | На недостачу складов подразделений и на личные списания. Там платят целиком, без покрытия заведением |
| Округление списаний | **Оставляем как в старом графе**: сумма каждой позиции округляется вверх до рубля |
| Кто относит списание к пулу | **Пока человек**, вручную. Обучение агента на этой классификации — потом, не в этапе 1 |
| Утверждение распределения | **Не нужно.** Строка в ведомость ставится автоматически, без промежуточного согласования |
| Где настройка | Карточка заведения → вкладка «Инвентаризация», блок правил. Поле «Лимит за счёт заведения» там уже есть и уже хранится на заведение |
| Склад решает плательщика | Инвентаризация по складу «Кальяны Сейф» / «Кальяны Зал» ложится на **кальянное подразделение**, а не на всю команду. Нужна привязка складов к подразделениям |
| Распределение | Сумма с команды делится по **процентам подразделений**, а внутри подразделения — пропорционально сменам: доля подразделения × (смены сотрудника ÷ все смены подразделения за месяц) |
| Запуск удержания | **Проведением акта в Sheerly**, который автоматически проводит акт в Quick Resto. На момент закрытия акта списания должны быть в ведомости |
| Где ещё видна сумма | **Нигде.** Только зарплатная строка: сотрудник получил меньше, и на этом всё. Проводки в Adesk или кассе не возникает |

## 3. Цели, не-цели, анти-цели

**Цели**
1. Каждая перенесённая цепочка имеет в Sheerly ровно одного исполнителя, и старый
   сценарий n8n после этого выключен.
2. Октябрьские данные и действующие настройки доступны в Sheerly и сходятся
   с источником по устойчивым исходным ID.
3. Ноябрь не накапливает нового разрыва: цепочка либо уже в Sheerly, либо
   осознанно остаётся в n8n до своей очереди.

**Не-цели этого прохода**
- Отказ от Adesk и перенос его истории (отдельный этап по решению владельца).
- Перенос складской Telegram-цепочки и приготовлений.
- Полные архивы вне октября, заготовка банковских реквизитов, подарки из Notion,
  задачи с фотоотчётами, тесты и связанные надбавки.
- Публичный API (политика репозитория не менялась).

**Анти-цели — то, что делает работу проваленной, даже если формально «работает»**
- Два реальных исполнителя одной операции хотя бы на один день: двойное списание
  бонусов, двойная выплата, двойное удержание. Здесь «исполнитель» — тот, кто
  **пишет**. Режим «Sheerly считает и показывает расхождения, но не пишет»
  анти-целью не является и остаётся основным способом приёмки (раздел 6.1).
- Сценарий n8n выключен раньше, чем нативный доказал себя на реальном рабочем дне.
- «Перенос» подтверждён видом экрана, зелёным CI или наличием кода вместо
  проверенного действия на сервере с повторным чтением результата.
- Новая сущность выдана за перенос: пустой экран Glide не становится работающей
  функцией из-за того, что в Sheerly нарисовали новый.

## 5. Ограничения

- **Прод self-hosted**, миграции катятся по SSH, реестр `schema_migrations` пассивный:
  строка вставляется после применения. Переименование уже применённой миграции
  ломает реестр — поэтому раздел 8.0 предлагает решение, а не просто `git mv`.
- **Telegram в n8n — не бот, а пользовательский аккаунт по MTProto через локальный
  Telegram MCP на NAS.** Поэтому он умеет ставить реакции и отвечать «от человека».
  Sheerly на Coolify так не умеет: бот не может ни ставить реакции от имени владельца,
  ни читать историю группы. Это не «допилить» — это другая архитектура. Решение
  владельца оставить цепочку в n8n снимает вопрос на этот проход.
- **Quick Resto — единственный источник фактов о сменах, чеках и остатках.**
  Ограничение частоты запросов уже учитывается существующими обработчиками.
- **Фоновые запуски** идут через `/etc/cron.d/crm-payroll-sales` → `crm-module-workers`
  раз в минуту под `flock`. Второй планировщик не создаём.
- **`PAYROLL_BONUS_WRITES_ENABLED` выключен** на проде. Реальные бонусные операции
  Quick Resto пока только за n8n.

## 6. Что значит «сценарий перенесён»

Этап не закрывается, пока не выполнены все семь пунктов. Это и есть определение
готовности, одинаковое для каждой цепочки.

1. Исходный сценарий прочитан в опубликованной версии (не в черновике), его
   фактическое поведение описано, включая защиту от дублей и поведение при обрыве.
2. В Sheerly есть интерфейс, права, сохранение и история действий.
3. Данные сопоставлены по **устойчивым исходным ID**. Совпадение имени или суммы
   доказательством отсутствия дубля не является.
4. Проверен реальный рабочий день: новые данные → начисление/деньги → ручное
   исправление → повтор → история и уведомления. Результат перечитан из БД.
5. Зафиксирован единственный исполнитель цепочки, старый сценарий n8n **выключен
   по-настоящему** (раздел 6.2), а кнопка в Glide, которая его запускала, убрана
   или обезврежена (раздел 6.3).
6. Записан порядок отката: при чём именно возвращаем n8n и как он не переобработает
   день, уже закрытый нативно.
7. Запись об этом внесена в `docs/automation-migration/` с датой и тем, где
   результат доступен: локально, в PR или на сервере.

### 6.1. Как проходит приёмка, не заводя второго писателя

Пункт 4 требует проверенного реального дня **до** выключения n8n, а раздел 3
запрещает двух исполнителей. Разрешается это так: нативная цепочка сначала живёт
в режиме сравнения — считает на тех же входных данных, сохраняет результат и
показывает расхождения с тем, что сделал n8n, но ничего не пишет во внешние
системы и в деньги. Писателем весь этот период остаётся n8n.

Это не новая выдумка, а уже работающий в проекте приём: `bonus_mode=parallel`,
флаг `PAYROLL_BONUS_WRITES_ENABLED`, read-only двойники в самом n8n
(`CHILLING / Закрытие дня — проверка полноты без записи`, `цепочка — проверка
инкассаций без записи`). Каждый этап обязан предусмотреть такой режим, снимок
входа и сличающий отчёт — это входит в его объём, а не появляется потом.

Переключение — отдельное действие в один день: включаем запись в Sheerly,
в тот же день гасим n8n. Промежутка, где пишут оба, нет.

### 6.2. Что значит «сценарий выключен» в n8n

Переключатель `active` снимает только **триггеры**. Вызов через Execute Workflow
продолжает исполнять неактивный воркфлоу. А `CHILLING / Закрытие операционного дня`
вызывает именно так семь цепочек, которые план гасит на этапах 2 и 6:
`Учет оборота, чаевых и смен`, `Продажи / Бармены`, `Продажи / Кальянные Мастера`,
`Распределение по счетам и учёт чеков Антона`, `Учет стажа и знаний`,
`CHILLING Growth / Daily Metrics`, `Учет инкассаций и дополнительного дохода`
(проверено по `inventory-2026-10-28.json`).

Поэтому срез любой из этих семи включает **правку самого оркестратора** — удаление
или ветвление шага — и это отдельная задача внутри своего этапа, со своим откатом.
Без неё получится ровно запрещённое состояние: два писателя каждый день, причём
незаметно, потому что интерфейс n8n покажет сценарий выключенным.

Побочное следствие: по мере вырезания шагов «проверка полноты дня» теряет охват.
На этапе 10 оркестратор гасится целиком, но до того его проверки нужно сокращать
согласованно, а не оставлять ссылаться на вырезанные шаги.

### 6.3. Кнопки в Glide

Выключенный сценарий n8n и живая кнопка в Glide — это молча потерянная операция:
человек жмёт, ничего не происходит, и никто этого не видит. Поэтому каждый этап
закрывает ещё и вход: кнопка в Glide убирается или заменяется на явное
«делается в Sheerly», а у людей, которые ей пользовались, к этому моменту есть
аккаунт Sheerly с нужными правами и рабочим мобильным экраном
(см. [mobile-web.md](../../mobile-web.md)).

## 7. Развилка, которую нужно решить до этапа 2

Владелец сказал: переносим логику в Sheerly «пока ещё в связке с Adesk», а после
переноса выключаем сценарий. Для финансовых цепочек это означает, что **Sheerly
должен сам писать в Adesk** — иначе выключение сценария n8n оборвёт поток в Adesk.

Клиента Adesk в Sheerly нет. То есть этап 2 начинается с постройки интеграции:
клиент API, идемпотентность, журнал исполнения, сверка, обработка обрыва POST.
Это заметный объём — и он **одноразовый**, потому что от Adesk мы отказываемся.

Три варианта, разница существенная:

- **A. Построить писателя Adesk в Sheerly.** Честно следует словам владельца, каждая
  финансовая цепочка выключается сразу. Но это работа, которую потом выбросим.
- **B. Сначала неденежные цепочки, финансы позже.** Этапы 1, 3, 4, 6, 8 идут вперёд,
  финансовые сценарии остаются в n8n до отказа от Adesk. Ничего не выбрасываем,
  но «один учёт» наступает позже.
- **C. Ускорить отказ от Adesk** и перенести его историю раньше, чем планировалось.
  Тогда финансовые цепочки переключаются на Sheerly-only, а Adesk гасится в тот же
  момент. Самый короткий путь к цели, но самый рискованный шаг по деньгам.

**Моя рекомендация — B**, с переоценкой после этапа 1. Причина: вариант A тратит
недели на код с заранее известной датой смерти, а C трогает деньги раньше, чем
нативные финансы прошли хотя бы один полный проверенный день.

Это решение владельца, в документе оно не зафиксировано.

## 8. Этапы

Порядок выбран по зависимостям и риску: сначала то, что ничего не ломает и ни от
чего не зависит; деньги — после того, как рядом с ними появилась история и сверка.

### Этап 0 — нумерация миграций (блокирует локальную разработку)

Починить порядок применения. Семь timestamp-файлов уже на проде, поэтому простое
переименование сломает реестр. Варианты решения — выбрать один:
переименовать файлы и дописать строки реестра под новыми именами на проде;

#### 1.3. Формула владельца уже реализована в калькуляторе

Владелец 2 ноября описал расчёт так: сумма недостачи по актам идёт на команду,
лимит 10 000 ₽ — на команду; дальше у каждого подразделения свой процент, а внутри
подразделения сотрудник платит пропорционально своим сменам («всего 60 смен
в месяце, он отработал 10 → ещё 1/6 от доли подразделения»).

Прочитал `shared-shortage.ts` и `deduction-rules.ts`: **это ровно то, что там
написано.** Моя прошлая редакция утверждала обратное, и это было неверно.

- `companyShortage` даёт `company = min(total, лимит)`, `employees = max(0, total − лимит)`;
  неиспользованный остаток лимита премией не становится.
- При `distribution: "departments"` пул делится между группами по `share`,
  а внутри группы — по `personWeights`, то есть по сменам. Подмена должности
  учитывается отдельным весом того же сотрудника.
- `excludedDepartmentIds` исключает подразделение из распределения.
- Остаток копеек раздаётся по стабильному ключу, порядок ответа БД результат
  не меняет. Нераспределённая доля не перекладывается на остальных: результат
  помечается `incomplete`, а не тихо округляется.
- `multiplier` в новых правилах жёстко `1` (`departmentDraft`) — коэффициент 1,1
  действительно не применяется.

То есть считать заново нечего. `allocateSharedShortage` просто **никем не
вызывается** — проверил по всему `src/`, потребителей ноль. Объём этапа 1 — это
вход и выход калькулятора, а не сам расчёт:

1. **Сумма недостачи акта** — откуда её брать после проведения (суммы акта
   в Quick Resto появляются только после проведения, см. 1.5).
2. **Смены за календарный месяц по подразделениям** — собрать `ShiftWeight[]`,
   включая подмены должности.
3. **Сальдо месяца и общий лимит.** `companyShortage` применяет лимит к одному
   переданному `total`, а лимит у нас месячный, общий на заведение, и излишки
   зачитываются против недостач (1.7). Значит вход калькулятора — не сумма
   отдельного акта, а сальдо месяца: накопительный пересчёт со сторно прежних
   строк. Расчёт по каждому акту отдельно дал бы каждому свой лимит 10 000 ₽.
4. **Запись строк** в ведомость Sheerly и сличающий отчёт против колонки I (1.1).

Про октябрьские 5 339 ₽, которыми я мерил масштаб в прошлых редакциях: владелец
уточнил, что это **акты списаний** из Google-таблицы, а не итоги инвентаризации.
То есть вторая половина суммы (1.6) в ту цифру вообще не входила, и вывод
«сотрудники платят ноль» к полному удержанию не относится.

**И сама цифра уже другая: 3 ноября октябрь в таблице списаний стал 6 039 ₽.**
Источник живой — сумма закрытого месяца меняется задним числом. Значит сличающий
отчёт (1.1) обязан фиксировать момент снятия и показывать обе суммы с этой
отметкой, иначе расхождение будет гоняться за движущейся целью, и непонятно,
разошёлся расчёт или просто сдвинулся источник.

#### 1.4. Решения, которые принимаю я

Отмечаю явно, чтобы можно было оспорить при детализации этапа.

- Пишем в существующую `payroll_adjustments` с `kind='inventory'` — значение уже
  есть в схеме с миграции 244, отдельную сущность не заводим.
- Ключ идемпотентности — устойчивый ID исходного акта плюс сотрудник; повтор
  возвращает ту же строку.
- Исправление акта или новая версия правил **сторнируют** прежнюю строку и ставят
  новую, а не правят на месте: иначе теряется требуемый разделом 6 «повтор».
- Если зарплатный период уже закрыт, строка уходит в ближайший открытый с явной
  ссылкой на исходный период. Задним числом закрытый период не вскрываем.
- Для новых правил `split` всегда `once`: разделение на два периода владелец
  отменил. Легаси-версии с `pending`/`two_months`/`two_payments` остаются в истории
  как происхождение и в расчёт не берутся.

#### 1.5. Триггер — существующая финализация акта, точка подключения известна

Владелец: акты подгружаются из Quick Resto в Sheerly, инвентаризация проводится,
акт закрывается в Sheerly, и скрипт проводит его в Quick Resto — «это у нас
работает». Проверил: работает. `finalizeInventoryResults` проводит акт
через `warehouse.inventory.document.v2/action` (раздел 4). Предшественника строить
не нужно — я ошибался, когда перенёс «склад только зеркало» с актов списания
на акты инвентаризации.

Точка подключения: **после успешного проведения в Quick Resto и локальной
финализации**, в той же транзакции состояния, что ставит `results_finalized_at`.
Раньше нельзя — суммы акта в Quick Resto появляются только после проведения
(memory `quickresto_inventory_semantics`), то есть до проведения считать нечем.
Триггер владельца совпадает с технической реальностью.

Что из существующего поведения придётся уважать:

- **Повторный вызов на уже проведённом акте.** Финализация умеет полусбойное
  состояние (в QR проведён, локально не доехало). Удержание обязано быть
  идемпотентным по тому же ключу, иначе второй клик удвоит строку.
- **`reopenInventoryResults`** снимает `results_finalized_at`, не меняя статус.
  Значит повторная финализация после переоткрытия штатна — и должна сторнировать
  прежние строки, а не добавлять новые (решение 1.4).
- **Сверка перед проведением** может отменить проведение из-за расхождения
  (случай СВ340). Удержание в этом случае не ставится вообще — состояние
  «посчитали, но не провели» не должно оставлять следов в ведомости.
- **403 на проведении** уже разобран (memory `quickresto_backoffice_auth`): нет
  системной роли у backoffice-юзера в Quick Resto, лечится в админке QR, не кодом.

#### 1.6. Два источника и привязка складов к подразделениям

Самое существенное уточнение 2 ноября, и оно меняет форму расчёта.

**Источников два, и они складываются.** Недостача по актам инвентаризации плюс
акты списаний, которые заводят сотрудники: разбили графин — скинули, списали,
за это тоже платят. Октябрьские 6 039 ₽ — это только вторая часть (1.3).

Асимметрия в механике есть, но она меньше, чем я написал в прошлой редакции,
и это была моя ошибка. Акты инвентаризации Sheerly проводит (1.5), а акты
списаний только читает из Quick Resto. Для удержания чтения достаточно: акты
заводят сотрудники в Quick Resto, а `/documents/writeoffs` уже сложил их в базу
(октябрь: 55 актов, 136 позиций, 53 проведено). Считать вторую половину суммы
есть из чего, создавать списания в Sheerly для этого не требуется.

Что действительно отличается — **момент расчёта**. У инвентаризации есть
проведение акта в Sheerly, и это естественный триггер (1.5). У списаний такого
момента нет: они приезжают синхронизацией (текущий месяц ежедневно, прошлый —
в первые три дня). Значит вторая половина пересчитывается вместе с месячным
сальдо, а не в момент «кто-то нажал кнопку». Накопительный пересчёт с сторно,
который я уже выбрал для лимита (1.3), закрывает и это.

Открытым здесь остаётся не «умеем ли мы», а **какие списания считать**: по каким
причинам (в правилах есть `writeoffReasons`, например «Бой посуды») и округлять
ли каждую позицию вверх, как делал старый граф. Округление вверх завышает сумму
на ровном месте — см. раздел 11.

**Склад определяет, кто платит.** Инвентаризация по складу «Кальяны Сейф» или
«Кальяны Зал» — это недостача кальянного подразделения, а не всей команды.
Сейчас привязки нет: в `stores` есть только `local_venue_id` (заведение,
проставляется руками на `/org/stores`, пропагируется в акты триггером миграции 194).
Подразделения как сущность есть с миграции 158, `roles.department_id` тоже.

Предлагаю ровно тот же механизм, что уже работает для заведения: колонка
`stores.department_id`, nullable, с композитным FK `(account_id, department_id)`
по конвенции `docs/CONVENTIONS.md`, и редактирование на той же странице складов.
Три состояния, и третье важнее первых двух:

| Привязка склада | Кто платит |
| --- | --- |
| Подразделение указано | Только это подразделение, распределение внутри него по сменам; доли групп не применяются |
| Явно «общий» | Вся команда по долям подразделений — сегодняшнее поведение |
| Не задана | Расчёт **неполный**, а не нулевой: акт не распределяется, пока склад не настроен |

Третье состояние — не перестраховка. Калькулятор уже так себя ведёт:
нераспределённая доля не перекладывается на остальных, результат помечается
`incomplete`. Молчаливый ноль здесь был бы потерей денег, которую никто не заметит.

**Привязку нужно фиксировать в снимке расчёта.** Склад могут переназначить
в другое подразделение; правила недостачи версионируются, привязка склада — нет.
Если удержание читает её на лету, пересчёт старого акта тихо поменяет
плательщика. Поэтому `department_id` склада, состав смен и версия правил
фиксируются на момент расчёта — так же, как `finalized_*` поля уже фиксируют
строки акта.

**Снимок акта тоже брать финализированный.** Управленческая недостача считается
не из `qr_shortfall_sum`, а по строкам с учётом исключённых позиций и активных
пересортов (миграции 225, 234, `src/lib/inventory/list-documents.ts`). У строк
и пересортов уже есть `finalized_*` поля. Удержание обязано читать именно их,
иначе изменение исключения задним числом сдвинет уже выплаченное.

#### 1.7. Сальдо месяца, общий лимит и где он живёт

Решено владельцем 2 ноября.

**Излишки зачитываются против недостач между актами, по суммам.** Минус 5 000 ₽
в одном акте и плюс 2 000 ₽ в другом дают −3 000 ₽ к удержанию. Считается сальдо,
а не каждый акт отдельно.

Масштаб решения виден на присланном экране за 21 октября по складу «Основной»:
семь актов `+410,1`, `−1 412,7`, `+2 846,0`, `+1 417,1`, `−2 002,1`, `−352,9`,
`−13 169,5`. Сумма одних недостач — 16 937,2 ₽, сальдо — −12 264,0 ₽. После лимита
это 6 937,2 ₽ против 2 264 ₽ к удержанию, то есть втрое. Правило зачёта — не деталь
реализации.

Три следствия для расчёта.

- **Период зачёта — календарный месяц**, тот же, что у лимита. Иначе результат
  зависит от того, где провести границу: за день сальдо одно, за месяц другое.
- **Положительное сальдо даёт ноль, а не премию.** Схема `amount`
  в `deduction-rules.ts` отрицательных значений не принимает, поэтому сальдо
  нужно обнулять **до** вызова `companyShortage`, а не передавать как есть —
  иначе на месяце, где излишки перекрыли недостачи, zod бросит исключение.
- **В сальдо входят только проведённые акты.** На том же экране два крупнейших
  акта (СВ378 и СВ376) ещё «Готовы к проведению». До проведения сумм в Quick Resto
  нет (1.5), в расчёт они не идут, и картина дня до их проведения другая.

**Зачёт идёт внутри пула плательщиков** — решено владельцем 3 ноября. Излишек
по «Кальяны Зал» уменьшает недостачу кальянного подразделения и не уменьшает то,
что платит вся команда. Иначе кальянный излишек оплачивал бы недостачу бара.

Отсюда форма расчёта за месяц:

1. **Пул — это плательщик, а не склад.** Два склада, привязанных к одному
   подразделению, дают один пул. Склады с привязкой «общий» дают пул всей
   команды. Пулов столько, сколько подразделений с привязанными складами, плюс
   один общий и личные.

| Пул | Кто платит | Лимит заведения |
| --- | --- | --- |
| Общий: инвентаризация общих складов + акты списаний | вся команда: доли подразделений, внутри доли по сменам | **да**, 10 000 ₽ за месяц |
| Инвентаризация склада подразделения | это подразделение, по его сменам | **нет**, платит целиком |
| Личные списания | конкретный сотрудник целиком | **нет** |
2. **Сальдо считается по каждому пулу отдельно** и обнуляется, если вышло
   положительным. Пул с излишком вносит ноль, и его излишек никуда не переходит —
   он просто сгорает. Следствие стоит назвать вслух: на месяце, где одно
   подразделение в излишке, а другое в недостаче, удержание получится больше,
   чем при едином сальдо заведения. Это и есть смысл зачёта внутри пула.
3. **Лимит накрывает только общий пул** — уточнено владельцем 3 ноября.
   10 000 ₽ за календарный месяц на заведение закрывают инвентаризацию общих
   складов и акты списаний вместе. Недостача склада подразделения и личные
   списания покрытия заведения не получают: там платят с первого рубля.
   Пропорционального деления покрытия между пулами, которое я написал в прошлой
   редакции, не будет — покрытие целиком принадлежит общему пулу.
4. **Внутри пула** превышение распределяется как сейчас: пул подразделения —
   по сменам этого подразделения, общий пул — по долям подразделений, а внутри
   доли по сменам (1.3).

**Настройка уже на месте.** Владелец попросил держать лимит в карточке заведения,
в блоке правил инвентаризации — он там и есть: `/org/venues/<id>`, вкладка
«Инвентаризация», блок «Инвентаризация и удержания», поле «Лимит за счёт
заведения, ₽» (`stock-settings-tab.tsx`, значение `companyAllowance`). Хранится
на заведение, сохраняется новой версией правил с датой, автором и основанием.
Заводить отдельное место для настройки не нужно; в этапе 1 к ней добавляется
только привязка складов к подразделениям (1.6).

#### 1.8. Классификация списаний: пока человек

Решено владельцем 3 ноября: в какой пул попадает списание, решает человек.
Агента на этой классификации обучим позже — записано в `BACKLOG.md`, в этап 1
не входит. Из ручного решения вытекает механика.

- **Пометка живёт в нашей таблице, а не в зеркале.** `stock_writeoff_documents`
  переписывается синхронизацией: у записи есть `payload`, `source_hash`,
  `version`, `missing_at`, и повторное чтение месяца создаёт новую версию.
  Пометка внутри `payload` пропадёт при следующем чтении. Нужна отдельная
  таблица с ключом «аккаунт + заведение + внешний ID акта», чтобы классификация
  переживала и ресинк, и исчезновение акта из источника.
- **Уровень — акт, а не позиция** (моё решение). Акт заводят под одно событие:
  в октябре 55 актов на 136 позиций. Пометка по позициям — расширение, а не
  фундамент. Риск назову вслух: смешанный акт (графин в общий пул, табак
  в кальянный) целиком уедет одному плательщику.
- **Непомеченный акт даёт неполный расчёт, а не ноль.** Так же, как склад без
  подразделения (1.6). Месяц не считается готовым, пока все проведённые акты
  месяца не разнесены по пулам.
- **Список причин становится подсказкой, а не фильтром.** `writeoffReasons`
  в правилах («Бой посуды» и прочие) при ручном решении больше не определяет,
  идёт ли акт на сотрудников — он подсвечивает кандидатов в интерфейсе.
  Настройку не удаляем, но считать по ней нельзя.
- **Нужно отдельное право.** Просмотр списаний — `inventory.view_results`,
  ручная синхронизация — `inventory.sync_quickresto`. Разнесение по пулам меняет
  деньги сотрудников, поэтому это своё право, а не побочный эффект права
  на просмотр. Имя — в детализации этапа.

**Округление оставляем как в старом графе**: сумма каждой позиции командного или
сотруднического списания округляется **вверх** до рубля. Отдельно отмечу разницу,
которая видна в источнике: для личного потребления старый граф округлял позицию
до целого рубля, а не вверх (`docs/automation-migration/stock-writeoffs-2026-10-31.md`).
Эту разницу сохраняю как есть и сам не унифицирую — если она была случайной, скажите.

#### 1.9. Постановка строки — автоматическая

Решено владельцем 3 ноября: распределение не утверждается, строка уходит
в ведомость сама. Это снимает промежуточный шаг, но перекладывает вес на две
вещи, которые теперь обязаны работать.

- **Автоматически ставится только готовый расчёт.** У калькулятора есть
  состояние `incomplete` — нераспределённый остаток или участник без группы.
  Непривязанный склад (1.6) и непомеченный акт (1.8) дают его же. Такой месяц
  **не ставит частичную строку**: автоматическая постановка плюс молчаливая
  недостача распределения — это неверная сумма в ведомости, которую никто
  не поймает. Неполный месяц должен быть виден как «не посчитан», с перечнем
  того, чего не хватает.
- **Исправление идёт сторно, и это теперь единственный способ.** Раз ошибку
  не ловят на утверждении, её ловят после постановки: переоткрытие акта,
  перепометка списания, новая версия правил — всё сторнирует прежние строки
  и ставит новые (1.4). Закрытый зарплатный период не вскрываем, строка уходит
  в ближайший открытый со ссылкой на исходный.
- **Аномалию показываем, но не блокируем** (моё решение). У инвентаризации
  есть сверка строк перед проведением — она родилась из случая СВ340, где
  на экране было +89,25 ₽, а провелось +16 301,75 ₽. У списаний такой защиты
  нет, а теперь между ошибочным актом и ведомостью нет человека. Поэтому резкое
  отклонение месяца от обычного даёт уведомление, а не запрет: владелец выбрал
  автоматику, и превращать её в скрытое утверждение я не буду.
- **Сотрудник видит строку сразу.** Отдельного черновика у строки нет — это
  прямо следует из требования владельца, что на момент закрытия акта списания
  уже в ведомости.

### Календарная срочность: стаж с 10 ноября

Единственная жёсткая дата в документе, и она про деньги. С 10 ноября стаж начисляет
Sheerly (`experienceStartsOn` в `src/lib/payroll/calculate.ts`), а n8n-сценарий
`Учет стажа и знаний` гасится только на этапе 6 — и вызывается оркестратором
ежедневно, даже будучи `active:false` по триггерам.

Скорее всего конфликта не будет: сценарий пишет стаж только при действующей
аттестации, а тесты отменены и действующих результатов нет с 22 октября. Но
«скорее всего» здесь недостаточно. **До 10 ноября нужно прочитать его последние
исполнения и убедиться, что он пишет ноль.** Если нет — стажевую часть этапа 6
вытаскиваем вперёд. Отдельно: что делаем с флагом `tenure_requires_exam`
в правилах оплаты, раз тесты отменены.

## 12. Мои решения, не владельца

Отмечаю явно, чтобы их можно было оспорить.

- Порядок этапов 1–10. Недостача идёт первой, но после ответа про ведомость
  этап 1 — это расчёт и сверка без смены писателя (1.1).
- Лимит за календарный месяц считается накопительно по всем проведённым актам
  месяца, с пересчётом распределения целиком и сторно прежних строк — иначе
  каждый акт получит свой лимит 10 000 ₽ (1.3).
- Период зачёта излишков — календарный месяц, тот же, что у лимита: за день
  сальдо одно, за месяц другое, и границу надо задать явно (1.7).
- Положительное сальдо месяца даёт ноль к удержанию и не становится премией;
  обнуляется до вызова `companyShortage`, иначе zod бросит на отрицательной
  сумме (1.7).
- В сальдо входят только проведённые акты: до проведения сумм в Quick Resto нет (1.7).
- Лимит применяется только к общему пулу; пулы подразделений и личные списания
  идут в расчёт с нулевым покрытием, то есть `companyAllowance` для них 0 (1.7).
  В сегодняшнем калькуляторе лимит берётся из одной конфигурации на всё, так что
  это вход, который этапу 1 придётся задавать по пулу.
- Пул — это плательщик, а не склад: два склада одного подразделения дают один
  пул, склады «общий» дают пул всей команды (1.7).
- Вторая половина суммы считается по уже синхронизированным актам списаний
  Quick Resto; создавать списания в Sheerly для удержания не требуется, и мой
  прошлый вывод про «половину суммы» был неверен (1.6).
- Классификация акта по пулу хранится в своей таблице по внешнему ID акта,
  а не в зеркале QR: иначе её сотрёт ресинк (1.8).
- Классификация на уровне акта, не позиции; смешанные акты — известный риск,
  пометка по позициям остаётся расширением (1.8).
- Непомеченный акт делает месяц неполным, а не нулевым (1.8).
- `writeoffReasons` при ручном решении — подсказка в интерфейсе, а не фильтр
  расчёта (1.8).
- Разнесение по пулам требует отдельного права, а не права на просмотр (1.8).
- Разницу округления между командными и личными списаниями сохраняю как
  в источнике и сам не унифицирую (1.8).
- Неполный расчёт не ставит частичную строку: при автоматической постановке
  это была бы неверная сумма без человека на пути (1.9).
- Резкое отклонение месяца даёт уведомление, а не блокировку: владелец выбрал
  автоматику, и превращать её в скрытое утверждение я не буду (1.9).
- Сличающий отчёт фиксирует момент снятия обеих сумм: источник живой, октябрь
  в таблице списаний уже изменился с 5 339 ₽ на 6 039 ₽ (1.3).
- У списаний нет момента проведения в Sheerly, поэтому их половина пересчитывается
  вместе с месячным сальдо, а не по событию (1.6).
- Излишек пула, перекрывший его недостачу, сгорает и не уменьшает удержание
  в других пулах — прямое следствие зачёта внутри пула (1.7).
- Отдельного места для настройки лимита не заводим: поле «Лимит за счёт
