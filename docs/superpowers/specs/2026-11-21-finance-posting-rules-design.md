# Правила разнесения операций — дизайн

Дата: 21.11.2026. Согласовано с Павлом в обсуждении; пометка «(решение исполнителя)» — то, что предложил я и Павел может поправить.

## Зачем

Сейчас каждую операцию в «Финансы → Транзакции» разносят руками: статья, контрагент, заведение. В Adesk для этого есть «правила автоматизации», и у Павла их много — почти все однотипные: «контрагент X + счёт СБЕР Бизнес + расход → статья „Поставки“, проект CHILLING». «Финансы» в перспективе уходят с Adesk, поэтому нужны свои правила:

- меньше ручного разнесения уже сейчас, при ручном вводе;
- основа для операций, которые будут приходить из банков напрямую (интеграции, начатые с Codex; источник `bank_sync`) — импорт выписки 1С Павел отклонил;
- место, куда переедут правила из Adesk.

## Цели

- Правило: «если все условия выполнены → заполнить статью / контрагента / заведение».
- Правила создаёт и правит пользователь в интерфейсе; ничего не зашито в код (Павел одобрил правила только в настраиваемом виде).
- Правила срабатывают при ручном вводе операции.
- Дальше — разово к существующим операциям (с предпросмотром) и к операциям из банковских интеграций.
- Однотипные правила Adesk сворачиваются в одно (условие «контрагент — один из списка»).

## Не цели

- Автоматический импорт правил из Adesk. Павел пришлёт список, перенесём руками, по ходу сведём дубли.
- Импорт банковской выписки (1С ClientBankExchange).
- Действия Adesk «перевести часть суммы в фонд», «начислить на следующие месяцы», «учесть в обязательствах», «НДС», теги — у нас нет этих понятий.
- «Статья по умолчанию» в карточке контрагента (вариант Б, отклонён — логика должна жить в одном месте).
- Условие «ИЛИ». В Adesk его нет и оно не понадобилось; второй вариант — второе правило.

## Анти-цели (что сделает фичу провальной, даже если «работает»)

- Правило молча перетирает то, что человек выбрал сам.
- Непонятно, почему операция разнеслась именно так.
- Массовое применение меняет операции без предпросмотра или пишет по строке журнала на каждую операцию.
- Правило меняет операции, закрытые зарплатой (`finance_transaction_lock`, PR #691).

## Подходы (выбор сделан)

- **А. Только правила, с условием «контрагент — один из списка» — выбран.** Вся логика разнесения в одном месте «Финансы → Правила»; десяток правил Adesk становится одним; новый поставщик — одна галочка.
- Б. Умолчания в карточке контрагента + правила для особых случаев — отклонён: два места, нужен приоритет между ними, вопрос «почему подставилось это» становится трудным.

## Как это устроено

### Правило

- **Название** — необязательное (решение исполнителя). В списке правило читается фразой «Если … — статья …, заведение …», как в Adesk; название нужно, когда фраза длинная.
- **Условия** — одно или несколько, все через «И».
- **Действия** — одно или несколько: статья, контрагент, заведение. Хотя бы одно обязательно.
- **Включено / выключено.**
- **Позиция в списке** — задаёт приоритет.

### Условия (этап 1)

| Условие | Операторы | Значение |
| --- | --- | --- |
| Контрагент | один из / ни один из | несколько контрагентов из справочника |
| Группа контрагентов | одна из | группы контрагентов (решение исполнителя: так новый поставщик попадает в правило, когда его кладут в группу) |
| ИНН контрагента | равно | текст; сверяется с ИНН выбранного контрагента |
| Счёт | один из | счета и кассы |
| Тип операции | равно | приход / расход (переводы правилами не разносятся — у них нет статьи и контрагента) |
| Сумма | от – до | одна или обе границы |
| Описание | содержит / не содержит / равно / начинается с | текст, без учёта регистра и лишних пробелов |

«Назначение платежа», «ИНН плательщика из банка» и подобные банковские поля появятся на этапе банковской интеграции — у операции сейчас таких полей нет. Хранение условий должно позволять добавить новый вид условия без переделки (решение исполнителя: список условий в одной структуре «поле / оператор / значение»).

### Действия (этап 1)

- **Статья.** Список статей зависит от типа операции. Если в правиле нет условия на тип, разрешены статьи типа «смешанная» или правило требует указать тип (решение исполнителя: при выборе статьи с типом «приход»/«расход» условие на тип добавляется автоматически — чтобы статья расхода не попала на приход).
- **Контрагент.**
- **Заведение** (аналог «проекта» Adesk).

Банковские действия Adesk — «удалить операцию» (ваши пополнения по СБП), «сделать переводом», «разбить на части» — к этапу банковской интеграции.

### Приоритет

- Правила упорядочены, порядок меняется перетаскиванием в списке.
- **Каждое поле заполняет первое сверху подходящее правило, в котором есть это действие.** Пример: правило 1 ставит статью, правило 3 ставит заведение — операция получит оба.
- Правило заполняет **только пустые поля**. Выбранное человеком (или уже стоящее у операции) не трогается.
- Выключенные правила не участвуют.
- Порядок вычисления: сначала действие «контрагент» (оно может сделать подходящими правила с условием на контрагента), затем статья и заведение по уже известному контрагенту (решение исполнителя: два прохода, без бесконечных цепочек).

### Когда применяются

1. **Ручной ввод (этап 1).** В форме операции: как только заполнены поля, от которых зависит правило, пустые статья / контрагент / заведение подставляются сами. Рядом с подставленным полем — пометка «по правилу „…“» (ссылка на правило). Если человек потом меняет поле — это его выбор, правило больше его не трогает. Если человек меняет условие (другой контрагент), а поле было подставлено правилом — подстановка пересчитывается; поле, выбранное вручную, остаётся. Работает и при правке существующей операции, но только для пустых полей.

   **Заведение** (решение Павла). Заведение, которое форма подставила из фильтра страницы, — подсказка, а не выбор человека: правило может его заменить (с пометкой «по правилу»). Заведение или «Без заведения», выбранное человеком руками, правило не трогает. В форме для этого нужно различать «подставлено фильтром», «подставлено правилом» и «выбрано человеком».
2. **К существующим операциям (этап 2).** Из правила: «Применить к существующим» → предпросмотр «изменится N операций» со списком → подтверждение. Только пустые поля, только незакрытые зарплатой, только видимые пользователю. Операции без заведения считаются неразнесёнными (решение Павла); в предпросмотре с любой операции можно снять галочку — для осознанно общих расходов. Одна запись журнала на команду (как массовая правка `finance_bulk_update_transactions` из PR #691; там это миграция `372_transactions_bulk_update_audit.sql`, номер может сдвинуться при мерже).
3. **Операции из банковских интеграций (этап 3).** Правила применяются при поступлении операции с `source = 'bank_sync'` тем же вычислителем.

**Происхождение поля после сохранения** (решение исполнителя). На этапе 1 у операции не хранится, каким правилом заполнено поле: пометка живёт в форме, схема операций не меняется. На этапе 2 массовое применение видно в журнале (одна запись на команду, в ней правило). Для этапа 3, где формы нет, происхождение решается вместе с банковской интеграцией. «Создать правило по этой операции» строится от полей самой операции.

**Сотрудник с доступом к одному заведению** (решение исполнителя). Правила общие на аккаунт. Если действие «заведение» ставит заведение, которое человеку недоступно в форме, это действие пропускается, а статья и контрагент подставляются. Список правил читают все с доступом к операциям; заведения и счета, к которым у человека нет доступа, показываются в фразе как «другое заведение» / «другой счёт», без названий.

Вычислитель правил — одна чистая функция (решение исполнителя: TypeScript, рядом тесты `node:test`), её используют форма, массовое применение и банковский воркер. Два вычислителя (TS + SQL) разошлись бы.

### Где настраивается

- **Отдельный пункт «Правила» в меню «Финансов»**, после «Контрагентов». Не вкладка «Статей» — правило ставит не только статью.
- Страница-список по стандарту таблиц (`docs/design-system.md`, memory `feedback_table_standardization_checklist`): каждое правило — фраза «Если … — …», переключатель вкл/выкл, перетаскивание для порядка, поиск по любому полю правила.
- Создание и правка — боковая панель (как в Adesk): блок «Если» со строками «поле / оператор / значение» и «Добавить условие», блок «Тогда» с «Добавить действие».
- Удаление — с подтверждением. Архива нет (решение исполнителя, отступление от `docs/CONVENTIONS.md` §2): у правила нет зависимых данных, «выключено» уже играет роль архива. Если Павел хочет архив — добавим триплет.

### Права

- **Видеть правила** — у всех, у кого есть доступ к операциям (`finance.view_transactions`): иначе при вводе непонятно, откуда взялась статья.
- **Настраивать** (создавать, править, менять порядок, удалять, применять к существующим) — новое право «Настраивать правила разнесения» (`finance.manage_posting_rules`), по умолчанию у владельца.

### Журнал

События `finance.posting_rule.created / updated / deleted / reordered`, на этапе 2 — `finance.posting_rule.applied` (одна строка: правило, сколько операций, какие поля). Подставленное при ручном вводе отдельно не журналируется — это часть создания операции.

### Данные

Новая top-level таблица правил аккаунта: `account_id` + композитный `UNIQUE (account_id, id)`, ссылки на статью / контрагента / заведение / счета — через композитные FK там, где это отдельные колонки (`docs/CONVENTIONS.md` §1). Что делать, когда статью / контрагента / заведение из правила архивируют или удаляют — решение исполнителя (предложение: правило остаётся, но в списке помечено «требует внимания» и не срабатывает).

## Этапы

1. **Правила и ручной ввод.** Таблица, право, страница «Правила», панель правки, перетаскивание, вычислитель с тестами, подстановка в форме операции с пометкой, handbook `docs/handbook/finance/rules.md`. Начинать после мержа PR #691 (он переписывает форму и список операций). Номер миграции — из `origin/main`.
2. **Существующие операции и перенос из Adesk.** «Применить к существующим» с предпросмотром и одной строкой журнала; кнопка «Создать правило по этой операции» в панели операции; перенос правил Павла из Adesk со сведением дублей.
3. **Банковские интеграции.** Применение к `bank_sync`, банковские поля в условиях (назначение платежа, ИНН и счёт плательщика), действия «не загружать / удалить», «сделать переводом». Перед началом — выяснить у Павла состояние интеграции, начатой с Codex.
