# Платформенное ядро — Техническое задание (Этапы 1–2)

## Контекст

Это первый и фундаментальный этап разработки мульти-тенантной платформы для заведений.
Стек: **Next.js (App Router) + Supabase** (Auth, PostgreSQL, RLS, Storage).

Всё, что закладывается здесь, должно быть универсальным и масштабируемым под будущие модули:
CRM, бронирования, графики, зарплата, склад и т.д.

---

## Принципиальные решения

- **Аккаунт ≠ Сеть.** Аккаунт — это просто владелец, который может иметь одно или несколько заведений. Никакой обязательной «сети» нет. Заведения объединяются в рамках одного аккаунта.
- **Автономное заведение** — частный случай: аккаунт с одним заведением. Архитектурно это то же самое, никаких развилок в RLS.
- **Права хранятся в БД**, не хардкодятся. Таблица `role_permissions` с флагами на каждое действие — в будущем настраивается через UI.
- **Приглашения сотрудников** — через Supabase Magic Link (email). Владелец вводит email и роль, сотрудник получает письмо и регистрируется по ссылке.
- **Часовой пояс** хранится на уровне заведения. Все временны́е расчёты ведутся относительно него.
- **Активное заведение** хранится в профиле пользователя (`active_venue_id`). Все RLS-политики будущих модулей будут опираться на это поле.

## Этап 1. Платформенное ядро

### 1.1 Аутентификация

Реализуется через **Supabase Auth**.

**Флоу:**
- Регистрация по email + пароль. После регистрации создаётся запись в `profiles` и первый `account`.
- Логин по email + пароль.
- Восстановление доступа — стандартный Supabase reset password flow (письмо со ссылкой).
- Приглашение сотрудника — Magic Link. Владелец вводит email и роль → сотрудник получает письмо → переходит по ссылке → попадает на экран завершения регистрации (имя, фамилия, пароль).

**Таблицы:**

`profiles`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid (FK → auth.users) | Первичный ключ |
| `first_name` | text | Имя |
| `last_name` | text | Фамилия |
| `phone` | text | Телефон |
| `photo_url` | text | Фото (Supabase Storage) |
| `active_venue_id` | uuid (FK → venues) | Текущее активное заведение |
| `created_at` | timestamptz | — |

---

### 1.2 Мульти-тенантная модель

**Структура:**

```
Account (аккаунт владельца)
└── Venue (заведение)
└── Venue (заведение)
└── ...
```

Пользователь привязан к аккаунту через владение или к конкретным заведениям через роли.

**Таблицы:**

`accounts`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `name` | text | Название аккаунта / бренда |
| `logo_url` | text | Логотип |
| `owner_id` | uuid (FK → profiles) | Владелец аккаунта |
| `created_at` | timestamptz | — |

`venues`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `account_id` | uuid (FK → accounts) | Принадлежность аккаунту |
| `name` | text | Название заведения |
| `logo_url` | text | Логотип |
| `type` | enum | `restaurant` / `bar` / `cafe` / `club` / `other` |
| `address` | text | Адрес |
| `phone` | text | Телефон |
| `currency` | text | Валюта (ISO 4217, например `RUB`, `USD`) |
| `timezone` | text | Часовой пояс (IANA, например `Europe/Moscow`) |
| `working_hours` | jsonb | Часы работы по дням недели (см. ниже) |
| `created_at` | timestamptz | — |

Формат `working_hours`:
```json
{
  "mon": { "open": "10:00", "close": "23:00", "closed": false },
  "tue": { "open": "10:00", "close": "23:00", "closed": false },
  "sun": { "closed": true }
}
```

`user_venue_roles` — связь пользователя с заведением и ролью
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `user_id` | uuid (FK → profiles) | Пользователь |
| `venue_id` | uuid (FK → venues) | Заведение |
| `role_id` | uuid (FK → roles) | Роль |
| `invited_by` | uuid (FK → profiles) | Кто пригласил |
| `created_at` | timestamptz | — |

### 1.3 Роли и права

**Таблицы:**

`roles`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `account_id` | uuid (FK → accounts) | Принадлежность (null = системная роль) |
| `name` | text | Название роли |
| `code` | text | Код роли (уникальный) |

Системные роли (создаются при инициализации):

| code | Название |
|---|---|
| `owner` | Владелец |
| `manager` | Управляющий |
| `admin` | Администратор |
| `hostess` | Хостес |
| `waiter` | Официант |

`permissions`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `code` | text | Код действия (уникальный) |
| `description` | text | Описание |
| `module` | text | Модуль (`platform`, `crm`, `staff`, `warehouse`, ...) |

`role_permissions` — матрица прав
| Поле | Тип | Описание |
|---|---|---|
| `role_id` | uuid (FK → roles) | Роль |
| `permission_id` | uuid (FK → permissions) | Право |
| `granted` | bool | Разрешено или нет |

**Начальный набор прав (модуль `platform`):**

| Код права | Описание |
|---|---|
| `platform.manage_account` | Управление аккаунтом |
| `platform.manage_venues` | Создание и редактирование заведений |
| `platform.manage_staff` | Управление сотрудниками |
| `platform.manage_roles` | Управление ролями и правами |
| `platform.view_analytics` | Просмотр аналитики |
| `platform.manage_settings` | Настройки заведения |

*Права будущих модулей (crm.*, staff.*, и т.д.) добавляются при реализации соответствующих модулей.*

**Матрица прав по умолчанию:**

| Право | owner | manager | admin | hostess | waiter |
|---|---|---|---|---|---|
| `platform.manage_account` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `platform.manage_venues` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `platform.manage_staff` | ✅ | ✅ | ❌ | ❌ | ❌ |
| `platform.manage_roles` | ✅ | ❌ | ❌ | ❌ | ❌ |
| `platform.view_analytics` | ✅ | ✅ | ✅ | ❌ | ❌ |
| `platform.manage_settings` | ✅ | ✅ | ❌ | ❌ | ❌ |

**RLS-политики:**

- Каждая таблица будущих модулей содержит `venue_id`.
- RLS проверяет: есть ли у текущего пользователя запись в `user_venue_roles` для этого `venue_id`.
- Дополнительно — проверка конкретного права через `role_permissions`.
- Вспомогательные функции в Supabase:
  - `get_active_venue_id()` — возвращает `active_venue_id` текущего пользователя.
  - `has_permission(permission_code text)` — проверяет наличие права у текущего пользователя в активном заведении.

## Этап 2. Онбординг и базовые настройки

### 2.1 Онбординг нового владельца

После регистрации владелец проходит пошаговый wizard. Каждый шаг сохраняется по мере заполнения. Wizard можно пропустить и вернуться из настроек.

**Шаг 1 — Профиль аккаунта**
- Название аккаунта (бренда или своё имя).
- Логотип (загрузка в Supabase Storage).

**Шаг 2 — Первое заведение**
- Название.
- Тип заведения.
- Адрес.
- Контактный телефон.
- Валюта.
- Часовой пояс.
- Часы работы по дням недели.

**Шаг 3 — Приглашение сотрудников** *(опционально, можно пропустить)*
- Поле для ввода email.
- Выбор роли из списка.
- Кнопка «Отправить приглашение» — отправляет Magic Link через Supabase Auth.
- Можно добавить несколько приглашений сразу.

**Шаг 4 — Готово**
- Краткий тур по интерфейсу (UI-подсказки).
- CTA: перейти в панель управления.

---

### 2.2 Управление сотрудниками

Доступно в настройках заведения. Права: `owner`, `manager`.

**Список сотрудников:**
- Имя, фамилия, фото, роль, дата добавления, статус (`active` / `invited` / `deactivated`).

**Приглашение:**
- Ввод email + выбор роли.
- Отправка Magic Link через Supabase Auth.
- До принятия приглашения сотрудник отображается со статусом `invited`.

**Редактирование:**
- Смена роли.
- Деактивация (не удаление — сохраняется история действий).

**Таблица приглашений:**

`invitations`
| Поле | Тип | Описание |
|---|---|---|
| `id` | uuid | Первичный ключ |
| `venue_id` | uuid (FK → venues) | Заведение |
| `email` | text | Email приглашённого |
| `role_id` | uuid (FK → roles) | Назначаемая роль |
| `invited_by` | uuid (FK → profiles) | Кто пригласил |
| `status` | enum | `pending` / `accepted` / `expired` |
| `created_at` | timestamptz | — |
| `expires_at` | timestamptz | Срок действия ссылки |

## Этап 3. UI Shell

Базовая оболочка приложения, которая связывает всё вместе. Реализуется параллельно с Этапом 2.

**Компоненты:**

- **Layout:** боковая навигация (sidebar) + верхняя панель (header) + контентная область.
- **Переключатель заведений:** выпадающий список доступных заведений пользователя. При выборе обновляется `active_venue_id` в `profiles`. Все последующие запросы идут в контексте нового заведения.
- **Навигация:** формируется динамически на основе прав пользователя. Пункты меню, на которые нет прав, не отображаются.
- **Профиль пользователя:** имя, фото, кнопка выхода, ссылка на настройки профиля.
- **Заглушки модулей:** разделы будущих модулей (CRM, Персонал и т.д.) присутствуют в навигации в виде неактивных пунктов — так видна общая структура платформы.

## Порядок реализации

1. БД: таблицы, enum-типы, RLS-политики, вспомогательные функции.
2. Supabase Auth: регистрация, логин, reset password, magic link для приглашений.
3. API / Server Actions: CRUD для аккаунта, заведений, ролей, приглашений.
4. UI Shell: layout, переключатель заведений, динамическая навигация.
5. Онбординг: wizard (шаги 1–4).
6. Управление сотрудниками: список, приглашение, смена роли, деактивация.
7. Настройки заведения: редактирование профиля заведения.
