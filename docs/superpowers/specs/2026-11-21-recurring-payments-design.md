# Повторяющиеся платежи и очередь «На разбор» — дизайн

Дата: 21.11.2026. Обсуждено с Павлом в сессии после аудита страницы «Транзакции».

## Зачем

Аренда, связь, налоги, подписки повторяются в одни и те же дни. Сейчас каждую такую операцию вводят руками и о сроке помнят сами. Нужно: один раз описать платёж — и дальше в срок система сама приносит его «на разбор» с заполненными полями, а когда подключится банк, сама находит пришедшую из банка операцию и разносит её по статье.

Павел сознательно **не хочет** уведомлений в колокольчике и в Telegram. Образец — Adesk: красная плашка «6 операций без статьи», окно «Распределить сейчас / позже / больше не напоминать», разбор по одной карточке. Наша очередь должна в будущем принять и банковские операции без статьи — это один и тот же поток работы «деньги, по которым нужно решение».

## Цели

- Шаблон повторяющегося платежа создаётся из существующей операции («Сделать повторяющейся» в меню строки, рядом с «Копировать») и редактируется на отдельной странице «Финансы → Повторяющиеся».
- В срок появляется **ожидаемый платёж** — отдельная запись на каждый наступивший период.
- Очередь «На разбор» показывает ожидаемые платежи карточками: провести, пропустить этот раз, перенести.
- Карточка висит, пока её не разберут. Просроченная помечается «просрочено N дн.».
- Счётчик очереди виден в сайдбаре и плашкой в шапке сводки «Финансов» и «Транзакций».
- После подключения банка ожидаемый платёж ждёт банковскую операцию и сопоставляется с ней сам (этап 3).

## Не цели

- Колокольчик, web push, Telegram — не делаем (решение Павла: карточка и так висит до разбора; можно добавить позже поверх).
- Статус «запланирована» у самой операции — не вводим.
- Платёжный календарь / прогноз остатков — не в этой работе.
- Автоматическое создание операции без участия человека, пока банк не подключён.

## Анти-цели (провал, даже если «работает»)

- Остатки счетов меняются от того, чего ещё не было: ожидаемый платёж **не является** операцией и не влияет на остатки, сводку, отчёты, экспорт.
- Двойной учёт: одна и та же аренда и проведена из карточки, и пришла из банка.
- Правка шаблона молча переписывает прошлые периоды.
- Пропущенные периоды схлопываются или исчезают: два пропущенных месяца связи = две карточки.

| Вопрос | Решение | Чьё |

| Что в срок | Ожидаемый платёж в очереди «На разбор»; без банка проводится вручную карточкой, с банком — ждёт банковскую операцию и сопоставляется | Павел |
| Где напоминать | Только очередь в «Финансах»: плашка, счётчик в сайдбаре, окно при входе (этап 2). Не колокольчик, не Telegram | Павел |
| Пропущенный срок | Карточка висит до разбора, с пометкой просрочки; у каждого периода своя карточка | Павел (висит), моё (по карточке на период) |
| Хранение сроков | Отдельная запись на каждый срок (не вычисление на лету, не статус операции) | Павел выбрал из трёх |
| Расписание | Ежемесячно N-го числа или в последний день месяца; еженедельно в выбранный день; ежеквартально (N-е число первого/второго/третьего месяца квартала); дата начала; необязательная дата окончания; пауза. Выходные не переносим — окно сопоставления покрывает | моё |
| Сумма | Постоянная или «меняется» (в шаблоне — ориентир, точная вводится на карточке) | моё |
| Сопоставление с банком | Того же направления, тот же контрагент, дата в окне [срок − 5; срок + 10] дней; постоянная сумма — точное совпадение, меняющаяся — любая. ## Подходы (рассмотрены)

1. **Отдельная запись на каждый срок (выбран).** Ежедневная фоновая задача создаёт `finance_recurring_occurrences` по наступившим срокам. У записи свой статус и история; сопоставление с банком просто помечает её. Цена — таблица и ежедневный запуск.
2. **Вычислять сроки на лету из шаблона.** Меньше таблиц, но правка шаблона задним числом меняет прошлое, а «перенести» и сопоставление всё равно требуют хранить состояние.
3. **Статус «запланирована» у операции.** Отброшено: затрагивает остатки, сводку, отчёты, экспорт — всё, что считает операцию фактом.

## Модель данных (ориентир для плана)

`finance_recurring_templates` — шаблон (тенантность по `docs/CONVENTIONS.md`: `account_id`, `UNIQUE (account_id, id)`, композитные FK; жизненный цикл `archived_at/by`):
- поля операции: `type` (income/expense; переводы — см. «Оставлено строителю»), `legal_entity_id`, `venue_id`, `bank_account_id`, `category_id`, `counterparty_id`, `amount`, `amount_varies bool`, `currency`, `description`;
- `name` (по умолчанию — контрагент или статья);
- расписание: `frequency` (`monthly`/`weekly`/`quarterly`), `day_of_month` (1–31, где «последний день» — отдельный флаг или 0/-1), `weekday`, `quarter_month` (1–3), `starts_on`, `ends_on null`, `paused_at null`;
- `source_transaction_id null` — из какой операции создан;
- `created_by/at`, `updated_by/at`.

`finance_recurring_occurrences` — ожидаемый платёж:
- `template_id`, `due_date`, `UNIQUE (template_id, due_date)` — идемпотентность ежедневной задачи;
- снимок полей шаблона на момент создания (сумма, счёт, статья, контрагент, заведение, юрлицо) — чтобы правка шаблона не меняла уже появившиеся карточки;
- `status`: `pending` / `posted` / `matched` / `skipped`;
- `postponed_to date null` — перенос (карточка скрыта из очереди до этой даты);
- `transaction_id null` — проведённая/сопоставленная операция (FK композитный);
- `resolved_by/at`.

Порождение: SECURITY DEFINER-функция `finance_recurring_materialize()` создаёт записи для всех сроков в интервале `[materialize_from; сегодня]` (сегодня — по часовому поясу аккаунта), по которым ещё нет записи; вызывается из `src/app/api/cron/finance-recurring/route.ts` по образцу `medical-book-expiry-notifications`. `revoke execute … from public, anon, authenticated` + проверка через `has_function_privilege` (CLAUDE.md).

Точка отсчёта (мои решения, закрывают вопросы проверки дизайна):
- В шаблоне хранится `materialize_from date`. Её выставляют: создание шаблона, «возобновить» после паузы, правка расписания — всегда в «завтра» (а при создании из операции — в `max(завтра, дата исходной операции + 1 день)`). Значит: прошлое никогда не догоняется задним числом; месяцы на паузе не порождают карточек; смена 5-го на 20-е действует только вперёд, а уже появившиеся карточки остаются со своими сроками.
- Период исходной операции считается закрытым ею самой: шаблон, созданный 21.11 из операции 05.11 с расписанием «5-го», даст первую карточку 05.12, не 05.11.
- Ежедневную задачу на проде запускает crontab на хосте, как остальные `/api/cron/*` (строка crontab — шаг выката в плане, через SSH). Страховка: открытие очереди «На разбор» и расчёт счётчика тоже вызывают порождение для своего аккаунта (идемпотентно благодаря `UNIQUE (template_id, due_date)`), поэтому молчащий cron не оставит очередь пустой.

Удаление проведённой операции (моё решение): триггер на мягкое удаление `transactions` возвращает связанный ожидаемый платёж в `pending` (с `transaction_id = null`), и карточка снова в очереди — период не пропадает молча. Восстановление удалённой операции карточку не трогает: если её уже провели заново, восстановленная — просто ещё одна операция, как и сейчас.

Видимость (моё решение): ожидаемый платёж и шаблон видны тем же, кому видна операция с теми же юрлицом и заведением — RLS повторяет условие политики `transactions` (включая `finance.view_all_venues` для операций чужих заведений и без заведения). Счётчик в сайдбаре считает в той же области, то есть по тому, что пользователь реально может разобрать.

«Провести» — одна транзакционная серверная операция: создать `transactions` (source `manual`) и пометить запись `posted` с `transaction_id`; повторный клик не создаёт дубль (условие `status = 'pending'`). Журнал: `finance.recurring.created/updated/archived/restored/deleted` и `finance.recurring_occurrence.posted/skipped/postponed` через `writeAuditEvent`, с фразами в `src/lib/audit/format.tsx`.

## Интерфейс

- **Меню строки операции** (income/expense, не удалённая): «Сделать повторяющейся» → та же боковая панель, что у операции, предзаполненная, плюс раздел «Расписание» и переключатель «Сумма меняется».
- **«Финансы → Повторяющиеся»** — список по эталону таблиц DS: название, сумма (с «~» для меняющейся), расписание словами («каждый месяц 5-го»), ближайший срок, состояние (активен / на паузе). Меню строки: изменить, пауза/возобновить, архив; архив-страница по конвенции.
- **«Финансы → На разбор»** — разбор по одной карточке со стрелкой «дальше» и счётчиком «осталось N». Карточка ожидаемого платежа:

  ```
  АРЕНДА · срок 05.12 · просрочено 2 дн. · Т-Банк · ООО «Арендодатель»
  150 000 ₽                         ← редактируется (обязательно, если «сумма меняется»)
  Статья: Аренда · Заведение: …     ← из шаблона, можно поменять
  [Провести]  [Пропустить этот раз]  [Перенести]
  ```

  Дата проведения по умолчанию — сегодня, можно поменять.
- **Счётчик**: бейдж у пункта сайдбара «На разбор» (механизм `badge` уже есть, прецедент — новые кандидаты) и красная плашка «N платежей ждут разбора» в шапке сводки «Финансов» и «Транзакций».
- Окно «Разобрать сейчас / Позже / Больше не напоминать» при входе в сводку — этап 2.

## Этапы

1. **Шаблоны и ожидаемые платежи.** Таблицы, ежедневное порождение, «Сделать повторяющейся», страница «Повторяющиеся» (+ архив), очередь «На разбор» с карточками ожидаемых платежей, счётчик в сайдбаре и плашка, журнал, справка `docs/handbook/finance/recurring.md`.
2. **Операции без статьи в той же очереди** и окно при входе в сводку (настройка «больше не напоминать» — на пользователя).
3. **Сопоставление с банком** — когда будет готова интеграция (начата с Codex; перед стартом спросить о её состоянии). Применяется при появлении операции `source = 'bank_sync'`.
